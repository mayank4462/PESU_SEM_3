# 1. Cookies

## What is a Cookie?

A **cookie** is a piece of data stored on a user's computer by a website/HTTP server.

Cookies allow websites to maintain some **state** between HTTP requests.

### Why are cookies needed?

Recall:

> **HTTP is stateless.**

The server normally does not remember previous requests.

Cookies provide a mechanism to maintain state across multiple HTTP transactions.

---

# 2. Cookie Components

The lecture identifies **four components** involved in maintaining user/server state:

1. **Cookie header line** in the HTTP response message
2. **Cookie header line** in the HTTP request message
3. **Cookie file** kept on the user's host and managed by the browser
4. **Back-end database** at the Web site

### Remember

```
Server → Set-Cookie → Browser
Browser → Cookie → Server
```

---

# 3. How Cookies Work

Suppose Susan visits an online shopping website for the first time.

### Step 1

Susan's browser sends a normal HTTP request.

### Step 2

The server creates a unique ID.

Example:

```
cookie: 1678
```

### Step 3

The server sends a response containing:

```
Set-Cookie: 1678
```

### Step 4

The browser stores the cookie.

### Step 5

On later requests, the browser sends:

```
Cookie: 1678
```

### Step 6

The server uses this cookie to identify Susan and access the corresponding information in its backend database.

```
Browser
   |
   | Cookie: 1678
   ↓
Web Server
   |
   ↓
Backend Database
   |
   → User information
```

---

# 4. Why Cookies Are Used

Cookies can be used for:

- Tracking browsing history
- Remembering login details
- Authorization
- Tracking visitor count
- Shopping carts
- Recommendations
- Saving coupon codes
- Maintaining user state

---

# 5. First-Party vs Third-Party Cookies

## First-Party Cookie

A cookie associated with the website the user is directly visiting.

Example:

```
User → nytimes.com
       ↓
First-party cookie
```

## Third-Party Cookie

A cookie associated with another website/service embedded in the page.

Example:

```
User → nytimes.com
          ↓
       AdX.com
          ↓
Third-party cookie
```

### Important

Third-party cookies can allow advertising/tracking services to track user behavior across multiple websites.

---

# 6. Cookies and Privacy

Cookies can create privacy concerns because they may be used to:

- Track browsing behavior
- Track activity across multiple websites
- Build user profiles
- Deliver personalized advertisements

The lecture specifically distinguishes **first-party** and **third-party cookies** in the context of tracking.

# 7. Web Caches / Proxy Servers

A **Web cache**, also called a **proxy server**, acts as both:

- Client
- Server

### As a server

It receives requests from browsers.

### As a client

It sends requests to the origin server when the requested object is not available in its cache.

---

# 8. Purpose of Web Cache

Goal:

> **Satisfy client requests without contacting the origin server whenever possible.**

### Process

```
Client
  |
  ↓
Web Cache
  |
  ├── Object available?
  │       ↓
  │      YES → Return object
  │
  └── NO → Request from origin server
```

---

# 9. Cache Hit and Cache Miss

## Cache Hit

Requested object is already present in the cache.

```
Client → Cache
          ↓
       Object found
          ↓
       Client
```

No request to the origin server is necessary.

## Cache Miss

Object is not present in the cache.

```
Client → Cache → Origin Server
Client ← Cache ← Origin Server
```

The cache obtains the object from the origin server and can store it.

---

# 10. Why Web Caching?

Web caching can:

- Reduce response time
- Reduce traffic on institutional access links
- Reduce Internet traffic
- Improve performance

The lecture also notes that caches can provide content efficiently and may have privacy implications.

---

# 11. Web Cache Example

Suppose:

```
Access link = 1.54 Mbps
Web object = 100 Kbits
RTT = 2 sec
Request rate = 15 requests/sec
```

Without caching, a large amount of traffic can pass through the access link.

If the cache satisfies some requests locally, the access-link utilization falls.

---

# 12. Cache Hit Rate

Suppose:

```
Cache hit rate = 40%
```

Then:

```
Requests satisfied from cache = 40%
Requests going to origin servers = 60%
```

Therefore, only:

```
60%
```

of requests need to cross the access link.

---

# 13. Cache Utilization Calculation

The lecture gives:

```
60% × 15 requests/sec
```

Therefore:

```
9 requests/sec
```

need to access the origin servers.

For a 100-Kbit object:

```
9 × 100 Kbits
= 900 Kbits/sec
```

Compared with:

```
1.54 Mbps
```

the utilization becomes approximately:

```
0.58
```

The lecture uses this example to show how caching reduces access-link utilization and delay.

---

# 14. Caching and Delay

Without caching:

```
Internet delay + access-link delay + LAN delay
```

With caching:

A cache hit can avoid:

```
Internet delay
```

Therefore:

> **Caching reduces average end-to-end delay.**

---

# 15. Web Cache vs Origin Server

|Web Cache|Origin Server|
|---|---|
|Stores copies of objects|Stores original objects|
|Acts as client and server|Acts as server|
|Can satisfy cache hits|Provides original resource|
|Reduces network traffic|May experience higher load|

**Answer:**

2. The cache checks whether the requested object is available.
3. If available, the cache returns the object directly.
4. If unavailable, the cache requests the object from the origin server.


# 16. Conditional GET

A major problem with caching is:

> **The cached copy may be outdated.**

Conditional GET solves this problem.

The goal is:

> Do not send the object if the cached copy is still up-to-date.

---

# 17. How Conditional GET Works

The client sends:

```
If-Modified-Since: <date>
```

The server checks whether the object has changed.

### Case 1 — Object NOT modified

Server sends:

```
304 Not Modified
```

The client uses its cached copy.

### Case 2 — Object modified

Server sends the updated object.

```
HTTP/1.1 200 OK
```

---

# 18. Conditional GET Flow

```
Client → Server
         If-Modified-Since: <date>

Server checks object

       ↓
 ┌───────────────┐
 │ Changed?      │
 └───────────────┘
    ↓          ↓
   NO         YES
    ↓          ↓
  304         200
 Not Modified  + object
```

# 🟨 Conditional GET — 2 Marks

## Q7. What is Conditional GET?

**Answer:**

Conditional GET allows a client/cache to ask the server whether a cached object has changed. If it has not changed, the server responds with **304 Not Modified** instead of sending the object again.

---

# 🟥 Conditional GET — 4 Marks

## Explain Conditional GET with its working.

**Answer:**

1. Client/cache stores an object and its modification date.
2. Later, the client sends a request containing `If-Modified-Since`.
3. The server checks the object's modification date.
4. If the object has not changed, the server sends `304 Not Modified`.
5. The client uses its cached copy.
6. If the object changed, the server sends the updated object with `200 OK`.

# 29. Symmetric Encryption

Symmetric encryption uses the **same secret key** for encryption and decryption.

```
Plaintext
   |
   | Same Secret Key
   ↓
Encryption
   ↓
Ciphertext
   |
   | Same Secret Key
   ↓
Decryption
   ↓
Plaintext
```

### Problem

Both sides must securely obtain the same secret key.

---

# 30. Asymmetric Encryption

Asymmetric encryption uses:

- Public key
- Private key

The keys are different.

```
Public Key
     ↓
Encryption
     ↓
Ciphertext
     ↓
Private Key
     ↓
Decryption
```

### Important

The public key can be distributed publicly.

The private key must remain secret.

---

# 31. Public-Key Cryptography

The lecture uses public-key cryptography as part of TLS authentication/key establishment.

Basic idea:

```
Public key → Can be shared

```

# 36. TLS 1.3

TLS 1.3 improves the TLS handshake.

The lecture highlights:

> **TLS 1.3 can reduce the handshake to 1 RTT.**

---

# 37. TLS 1.3 — 1 RTT Handshake

Basic sequence:

### Step 1 — Client Hello

Client sends:

- Supported cipher suites
- Key-share parameters
- Other protocol parameters

### Step 2 — Server Hello

Server sends:

- Selected cipher suite
- Key-share parameters
- Certificate
- Other handshake information

### Step 3

Client verifies the certificate and sends/derives the necessary key material.

After the handshake, encrypted application data can be exchanged.

---

# 38. TLS 1.3 — 0 RTT

TLS 1.3 can also support **0-RTT** in certain situations, particularly for returning clients.

This can reduce latency because application data can be sent earlier.

### But important security issue

The lecture notes that **0-RTT data can be vulnerable to replay attacks**.

Therefore:

```
1-RTT → safer/general handshake
0-RTT → faster but replay concerns
```

---

# 39. TLS 1.3 vs Older TLS

|Feature|Older TLS|TLS 1.3|
|---|---|---|
|Handshake|More round trips|1 RTT|
|Returning client|Higher latency|Can use 0-RTT|
|Security|Older algorithms possible|Removes insecure/obsolete options|
|Performance|Higher latency|Lower latency|

# Q11. Explain TLS 1.3 handshake.

**Answer:**

TLS 1.3 improves connection setup by reducing the handshake to approximately **1 RTT**.

### Step 1

Client sends a **ClientHello** containing supported cipher suites and key-share information.

### Step 2

Server sends a **ServerHello**, selects parameters and sends certificate/key information.

### Step 3

Client verifies the certificate and completes the key establishment.

After this, encrypted application data can be transmitted.

---

# Q12. Explain 0-RTT in TLS 1.3.

**Answer:**

TLS 1.3 can support 0-RTT for returning clients.

Advantages:

- Reduces connection latency.
- Allows application data to be sent earlier.

Disadvantage:

- 0-RTT data can be vulnerable to **replay attacks**.

Therefore, applications must use 0-RTT carefully.

If you have **5 minutes before the exam**, memorize this:

```
COOKIE
→ Maintains state
→ HTTP itself is stateless
→ Cookie stored by browser
→ Server can maintain backend database
```

```
WEB CACHE
→ Proxy server
→ Acts as client + server
→ Cache hit → local object
→ Cache miss → origin server
→ Reduces delay + traffic
```

```
CONDITIONAL GET
→ If-Modified-Since
→ unchanged → 304 Not Modified
→ changed → 200 OK + object
```

```
HTTP/2
→ Reduce multi-object delay
→ Multiple requests
→ Priorities
→ TCP
→ HOL blocking possible
```

```
HTTP/3
→ UDP-based
→ Addresses TCP/HOL limitations
```

```
HTTPS
→ HTTP + TLS
→ Port 443
```

```
TLS
→ Confidentiality
→ Integrity
→ Authentication
```

```
SYMMETRIC
→ Same secret key
```

```
ASYMMETRIC
→ Public key + Private key
```

```
CERTIFICATE
→ Domain
→ Public key
→ Issuer
→ Expiry
→ CA signature
```

```
TLS 1.3
→ 1 RTT handshake
→ 0 RTT possible for returning clients
→ 0 RTT has replay-attack concern
```
