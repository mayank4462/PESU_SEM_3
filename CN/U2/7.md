# 2. Why Do We Need Reliable Data Transfer?

The slide on **page 3** asks:

> Why do we need reliable data transfer?

The answer:

> Applications may need data to be delivered correctly even when the underlying network is unreliable.

An application may expect:

```text
Data sent
   ↓
same data received
   ↓
correctly
```

But the underlying network may not guarantee that.

---

# 3. Unreliable Network — Possible Problems

The slide explicitly identifies these challenges:

1. **Bit errors / packet corruption**
2. **Packet loss**
3. **ACK loss**
4. **Packet duplication**
5. **Unknown receiver state**

These problems motivate the design of reliable-data-transfer protocols.

---

# 4. What Is Reliable Data Transfer?

Reliable data transfer means providing the application with a service that behaves as if the communication channel were reliable, even though the underlying channel may be unreliable.

Conceptually:

```text
Sending process
      ↓
Reliable transport service
      ↓
Receiving process
```

The application sees:

```text
correct data
in the correct order
without unintended duplicates
```

even though the underlying channel can:

```text
lose
corrupt
delay
duplicate
```

packets.

---

# 5. Reliable Service Abstraction

The diagram on **page 4** shows the abstraction.

At the application level:

```text
Sending process
      ↓
      data
      ↓
Reliable service
      ↓
      data
      ↓
Receiving process
```

The application does not need to know the details of how reliability is implemented.

The reliable-data-transfer protocol hides the unreliable behavior of the underlying network.

# 6. Reliable Data Transfer Is a Protocol Problem

The key question is:

> How can we build a reliable service on top of an unreliable channel?

The answer is to progressively add mechanisms.

Typical mechanisms include:

```text
Checksum
ACK
NAK
Sequence number
Timer
Retransmission
```

Each mechanism solves a particular problem.

# 8. Complexity Depends on the Channel

Possible channel behavior:


# 9. Sender and Receiver Do Not Know Everything

The slide on **page 7** highlights an important problem:

> Sender and receiver do not know the state of each other unless they communicate that state.

For example, the sender may not know whether:

```text

packet was corrupted
ACK was lost
receiver is waiting for another packet
```

Therefore the protocol needs feedback.

# 12. RDT Protocol Evolution

The slide on **page 9** summarizes the evolution:

| Version | Problem addressed | Main mechanisms |
|---|---|---|
| rdt1.0 | Perfect channel | None beyond basic send/receive |
| rdt2.0 | Bit errors | Checksum, ACKs, NAKs |
| rdt2.1 | Corrupted ACK/NAK and duplicate data | Sequence numbers + ACK/NAK |
| rdt2.2 | Bit errors without NAK | Sequence numbers + duplicate ACKs |
| rdt3.0 | Bit errors + packet loss | Timer, timeout, retransmission |

This progression is one of the highest-yield parts of the chapter.

# 13. rdt1.0 — Perfectly Reliable Channel

## Assumption

The underlying channel is perfect.

Therefore:

```text
No bit errors
No packet loss
No duplication
```

The sender can simply:

```text
send data
```

and the receiver can:

```text
receive data
deliver data
```

No ACK, NAK, sequence number, or timer is required.

---

# 14. rdt1.0 — Basic Operation

```text
Sender
  |
  | data packet
  ↓
Perfect channel
  |
  ↓
Receiver
  |
  ↓
deliver data
```

### Key point

rdt1.0 is simple because the channel itself is assumed reliable.

---

# 15. Why rdt1.0 Is Unrealistic

Real networks can experience:

```text
bit errors
packet loss
delays
duplicate packets
lost acknowledgments
```

Therefore we need more sophisticated protocols.

This leads to:

```text
rdt2.0
```

---

# 16. rdt2.0 — Channel With Bit Errors

rdt2.0 assumes:

```text
Packets are not lost
BUT
bits may be corrupted
```

Therefore the protocol needs a way to detect corruption.

Mechanism:

```text
Checksum
```

---

# 17. rdt2.0 — Checksum

The sender adds a checksum to the packet.

The receiver uses it to determine whether the packet was corrupted.

Conceptually:

```text
Sender
  ↓
packet + checksum
  ↓
unreliable channel
  ↓
Receiver
  ↓
check checksum
```

If valid:

```text
ACK
```

If corrupted:

```text
NAK
```

---

# 18. rdt2.0 — ACK and NAK

### ACK

ACK means:

```text
I received the packet correctly.
```

The sender can then send the next packet.

### NAK

NAK means:

```text
The packet was corrupted.
```

The sender retransmits the packet.

---

# 19. rdt2.0 Is Stop-and-Wait

The study notes emphasize that the sender cannot send the next data packet while waiting for the ACK/NAK for the current packet.

Therefore:

```text
send packet 0
     ↓
wait
     ↓
ACK/NAK
     ↓
send next packet
```

This is called:

> **Stop-and-wait**

Only one packet is effectively outstanding at a time.

---

# 20. rdt2.0 — Major Flaw

rdt2.0 handles:

```text
corrupted data packets
```

but initially fails to handle:

```text
corrupted ACK
corrupted NAK
```

What if the receiver correctly received the data, but the ACK becomes corrupted?

The sender cannot tell whether:

```text
data arrived correctly
```

or:

```text
data was corrupted
```

---

# 21. Why Corrupted ACK/NAK Is Dangerous

Suppose:

```text
Sender → Packet 0 → Receiver
```

Receiver correctly receives packet 0.

Receiver sends:

```text
ACK
```

But the ACK is corrupted.

Sender receives:

```text
garbled ACK
```

Now sender does not know what happened.

If it retransmits blindly:

```text
Receiver may get packet 0 twice.
```

Therefore we need to detect duplicates.

This leads to:

```text
rdt2.1
```

---

# 22. rdt2.1 — Sequence Numbers

rdt2.1 introduces:

```text
Sequence numbers
```

For stop-and-wait, a **1-bit sequence number** is enough:

```text
0
1
0
1
...
```

Why only 1 bit?

Because the sender has at most one unacknowledged packet in flight.

The receiver only needs to distinguish:

```text
new packet
vs
duplicate retransmission
```

---

# 23. rdt2.1 Sequence Number Operation

Suppose receiver expects:

```text
sequence 0
```

It receives:

```text
sequence 0
```

→ new packet.

It delivers it and then expects:

```text
sequence 1
```

If it receives sequence 0 again:

```text
duplicate
```

The receiver must not deliver the data again.

---

# 24. Why Sequence Numbers Solve Duplicate Delivery

Suppose:

```text
Packet 0
ACK 0
```

ACK gets lost.

Sender retransmits:

```text
Packet 0
```

Receiver sees:

```text
sequence number = 0
```

but it already accepted packet 0.

Therefore:

```text
discard duplicate
```

and send the appropriate ACK again.

---

# 25. rdt2.1 — ACK and NAK

rdt2.1 uses:

```text
ACK
NAK
```

The receiver can indicate:

```text
ACK → correctly received
NAK → corrupted
```

Sequence numbers allow the receiver and sender to distinguish which packet is being referenced.

---

# 26. rdt2.1 — Sender States

Because the sequence number alternates:

```text
0
1
```

the sender maintains states associated with:

```text
waiting for ACK/NAK 0
waiting for ACK/NAK 1
```

The study material describes the FSM as having roughly twice as many states as the simpler rdt2.0 FSM because the state must also represent whether packet 0 or packet 1 is currently being sent/expected.

---

# 27. rdt2.1 — Receiver States

Similarly, the receiver needs to know whether it is expecting:

```text
packet 0
```

or:

```text
packet 1
```

This expected sequence number is essential for detecting duplicates.

---

# 28. rdt2.2 — NAK-Free Protocol

rdt2.2 removes explicit NAKs.

Instead of:

```text
NAK
```

the receiver can send:

```text
duplicate ACK
```

for the last correctly received packet.

This is a major exam point.

---

# 29. How rdt2.2 Replaces NAK

Suppose receiver correctly received:

```text
Packet 0
```

It sends:

```text
ACK 0
```

Now packet 1 arrives corrupted.

Instead of:

```text
NAK 1
```

the receiver sends:

```text
ACK 0
```

again.

Therefore:

```text
duplicate ACK 0
```

implicitly means:

```text
packet 1 was not correctly received
```

---

# 30. Why ACKs Need Sequence Numbers in rdt2.2

The receiver's ACK must identify the packet being acknowledged.

For example:

```text
ACK 0
ACK 1
```

The sender checks the sequence number inside the ACK.

This prevents ambiguity.

---

# 31. rdt2.2 — Sender Interpretation

Suppose sender transmitted:

```text
Packet 1
```

and receives:

```text
ACK 0
```

That means:

```text
ACK is for an earlier packet.
```

Therefore packet 1 was not successfully acknowledged.

The sender retransmits packet 1.

---

# 32. rdt2.2 — Why Duplicate ACKs Matter

Duplicate ACK:

```text
same ACK received again
```

means the receiver is still acknowledging the last packet it successfully received.

Therefore the next packet is presumed not to have arrived correctly.

---

# 33. rdt2.2 — Main Improvement

```text
rdt2.1
    ↓
ACK + NAK
    ↓
rdt2.2
    ↓
ACK only
+
sequence-numbered duplicate ACKs
```

This is called:

> **NAK-free reliable data transfer**

for the bit-error case.

---

# 34. rdt3.0 — Lossy Channel

Now assume the channel can:

```text
corrupt packets
AND
lose packets
```

This creates a new problem:

> How does the sender know that a packet or ACK was lost?

The answer:

```text
Timer
```

---

# 35. rdt3.0 — Timer

After sending a packet, the sender starts a timer.

Conceptually:

```text
send packet
    ↓
start timer
    ↓
wait for ACK
```

If ACK arrives:

```text
stop timer
send next packet
```

If timer expires:

```text
packet/ACK presumed lost
        ↓
retransmit packet
```

---

# 36. Timeout

A timeout occurs when:

```text
expected ACK
```

does not arrive before the timer expires.

The sender assumes:

```text
packet lost
OR
ACK lost
OR
ACK excessively delayed
```

and retransmits.

---

# 37. Why Retransmission Is Safe

What if the original packet was actually received but its ACK was lost?

The retransmitted packet is a duplicate.

Sequence numbers allow the receiver to recognize:

```text
duplicate packet
```

and avoid delivering the same application data twice.

Therefore rdt3.0 combines:

```text
checksum
+
sequence numbers
+
ACKs
+
retransmission
+
timer
```

---

# 38. rdt3.0 — Packet Loss

The slide on **page 10** shows packet-loss behavior.

Normal case:

```text
send pkt0
     ↓
receive pkt0
     ↓
ACK0
     ↓
send pkt1
```

If a packet is lost:

```text
send pkt1
     X
   lost
```

Sender waits.

Eventually:

```text
timeout
```

Then:

```text
resend pkt1
```

---

# 39. rdt3.0 — ACK Loss

The slide on **page 11** shows ACK loss.

Sequence:

```text
Sender → pkt1 → Receiver
Receiver → ACK1 → X lost
```

Sender does not receive ACK1.

Therefore:

```text
timeout
```

Sender retransmits:

```text
pkt1
```

Receiver recognizes it as a duplicate using the sequence number.

Receiver:

```text
does not deliver duplicate data
sends ACK1 again
```

---

# 40. rdt3.0 — Premature Timeout / Delayed ACK

The slide also illustrates a **premature timeout** case.

Suppose:

```text
Packet arrives correctly
ACK is delayed
```

but the sender's timer expires before ACK arrives.

Sender retransmits.

The receiver may receive:

```text
duplicate packet
```

Sequence numbers prevent duplicate delivery.

This shows why timeout values matter.

```text

+

+

+

```

This handles:


# 42. RDT Evolution — One Table

| Version | Channel assumptions | Added mechanism |
|---|---|---|
| rdt1.0 | Perfect | Basic transmission |
| rdt2.0 | Bit errors | Checksum + ACK/NAK |
| rdt2.1 | Bit errors + corrupted ACK/NAK | Sequence numbers |
| rdt2.2 | Bit errors + corrupted ACK/NAK | Duplicate ACK instead of NAK |
| rdt3.0 | Bit errors + packet loss | Timer + timeout + retransmission |

### Memory

```text
1.0 → perfect
2.0 → checksum
2.1 → sequence number
2.2 → duplicate ACK / no NAK
3.0 → timer + retransmission
```

# 43. Stop-and-Wait

The slide diagrams on **pages 10–11** demonstrate stop-and-wait.

Basic operation:

```text
SEND
 ↓
WAIT
 ↓
ACK
 ↓
SEND NEXT
```

The sender does not continuously fill the channel.

Only one packet is outstanding.

---

# 44. Why Stop-and-Wait Is Reliable but Slow

Suppose:

```text
Packet sent
      ↓
wait for propagation
      ↓
receiver receives
      ↓
ACK travels back
      ↓
sender can send next packet
```

Most of the time can be spent waiting rather than transmitting.

This becomes severe when:

```text
RTT is large
```

and:

```text
transmission time is small
```

---

# 45. Stop-and-Wait Performance

The slide on **page 12** defines sender utilization:

```text
U_sender
=
fraction of time sender is busy sending
```

For stop-and-wait, the sender is active for approximately:

```text
L/R
```

where:

```text
L = packet length in bits
R = transmission rate in bits/sec
```

A simplified utilization expression is:

```text
U_sender
=
(L/R)
----------------
(RTT + L/R)
```

or:

```text
U_sender
=
L/R
-----------
RTT + L/R
```

assuming ACK transmission time is negligible.

---

# 46. Transmission Delay

Transmission delay:

```text
d_trans
=
L/R
```

where:

```text
L = packet size in bits
R = link transmission rate in bits/sec
```

This is the time required to push all packet bits onto the link.

---

# 47. Transmission Delay Example — Page 12

Given:

```text
Link rate R = 1 Gbps
Packet size L = 8000 bits
```

Then:

```text
d_trans = L/R
        = 8000 / 10^9
        = 8 × 10^-6 sec
        = 8 microseconds
```

So the sender takes only:

```text
8 μs
```

to transmit the packet into the link.

---

# 48. RTT Example — Page 13

The slide considers approximately:

```text
RTT = 30 ms
```

and:

```text
transmission time = 8 μs
```

Timeline:

```text
t = 0
↓
first packet bit transmitted

t = 8 μs
↓
last bit enters channel

      ↓ propagation

receiver gets packet

      ↓ ACK

t ≈ RTT + 8 μs
↓
ACK reaches sender
```

Only then can the sender send the next packet.

---

# 49. Stop-and-Wait Utilization Calculation

Using:

```text
L/R = 0.008 ms
RTT = 30 ms
```

we get:

```text
U_sender
=
0.008
---------
30.008
```

Therefore:

```text
U_sender ≈ 0.00027
```

or approximately:

```text
0.027%
```

This is extremely low utilization.

---

# 50. Why Utilization Is So Low

The sender:

```text
transmits for 0.008 ms
```

but waits approximately:

```text
30 ms
```

for the complete send/RTT cycle.

So:

```text
tiny transmission time
+
large waiting time
=
poor utilization
```

This is the central performance problem with stop-and-wait.

---

# 51. Page 14 — Protocol Performance Stinks

The slide emphasizes:

> rdt3.0 protocol performance stinks!

The reason is not that rdt3.0 is incorrect.

rdt3.0 is **functionally correct**.

The problem is:

```text
stop-and-wait
```

causes the sender/channel to remain idle for much of the time.

---

# 52. Correct vs Efficient

Important distinction:

```text
rdt3.0
=
correct reliable protocol
```

but:

```text
rdt3.0
≠
high-performance protocol
```

This distinction motivates:

```text
Pipelining
```

# 53. Pipelined Reliable Data Transfer

The slide on **page 15** introduces the solution.

Instead of:

```text
send 1
wait
send 2
wait
send 3
wait
```

allow:

```text
send 1
send 2
send 3
...
```

without waiting for each ACK individually.

This is:

> **Pipelining**

---

# 54. What Is Pipelining?

Pipelining allows:

```text
multiple packets
```

to be:

```text
in flight
```

at the same time.

Conceptually:

```text
Sender
  |
  | pkt0 →→→
  | pkt1 →→→
  | pkt2 →→→
  | pkt3 →→→
  |
  ↓
Receiver
```

ACKs return while additional packets are already traveling.

---

# 55. Why Pipelining Improves Utilization

Stop-and-wait:

```text
send
wait
send
wait
```

Pipelining:

```text
send send send send
      ↓
    ACK ACK ACK
```

The channel stays busy for a much larger fraction of the time.

---

# 56. Consequences of Pipelining

The study notes identify three important consequences.

### 1. Larger sequence-number range

There can be multiple unacknowledged packets simultaneously.

Therefore each in-flight packet needs a unique sequence number.

---

### 2. More buffering

The sender may need to store:

```text
sent but not yet acknowledged packets
```

The receiver may also need to buffer correctly received packets depending on the protocol.

---

### 3. More complex recovery

When packets are:

```text
lost
corrupted
delayed
```

the protocol must decide which packets to retransmit.

This leads to:

```text
Go-Back-N
Selective Repeat
```

---

# 57. Page 16 — Three-Packet Pipelining

The slide compares stop-and-wait with a pipeline of three packets.

For the same example:

```text
L/R = 0.008 ms
RTT = 30 ms
```

Three packets can be sent before waiting.

Approximate utilization:

```text
U_sender
=
3(L/R)
-----------------
RTT + L/R
```

Therefore:

```text
=
3 × 0.008
----------------
30.008
```

```text
≈ 0.0008
```

The slide emphasizes:

> 3-packet pipelining increases utilization by a factor of 3.

---

# 58. General Pipelining Intuition

If the sender can keep:

```text
N packets
```

in flight, utilization can increase substantially compared with stop-and-wait, especially when:

```text
N × transmission time
```

approaches the relevant round-trip waiting interval.

The exact utilization depends on the protocol and assumptions.

---

# 59. Stop-and-Wait vs Pipelining

| Feature | Stop-and-Wait | Pipelining |
|---|---|---|
| Packets in flight | Usually 1 | Multiple |
| Sender waits after each packet | Yes | No |
| Utilization | Low on high-RTT links | Higher |
| Sequence numbers | Small range can suffice | Larger range required |
| Buffering | Limited | More required |
| Complexity | Lower | Higher |
| Main issue | Idle waiting | More complicated loss recovery |

---

# 60. Go-Back-N — GBN

The study notes include Go-Back-N as the first major pipelined recovery approach.

GBN allows:

```text
multiple packets in flight
```

but limits the number of unacknowledged packets to a maximum:

```text
N
```

This is the:

> **GBN window size**

---

# 61. GBN Sender Window

The sender maintains a window of sequence numbers.

Important variables:

```text
base
nextseqnum
```

### `base`

Sequence number of:

```text
oldest unacknowledged packet
```

### `nextseqnum`

Sequence number of:

```text
next unused packet
```

---

# 62. GBN Sequence Number Regions

Conceptually:

```text
[0, base-1]
```

= already transmitted and acknowledged.

```text
[base, nextseqnum-1]
```

= transmitted but not yet acknowledged.

Then the usable sending window contains future sequence numbers.

---

# 63. GBN Cumulative ACKs

GBN uses:

> **Cumulative acknowledgments**

An ACK for packet `n` indicates that the receiver has correctly received packets through the relevant sequence point.

Conceptually:

```text
ACK 5
```

means:

```text
packets up through 5
```

have been successfully received in order.

---

# 64. GBN Sender Timeout

GBN uses a timer associated with the oldest outstanding packet.

If timeout occurs:

```text
retransmit all outstanding unacknowledged packets
```

Example:

```text
sent:
0 1 2 3

ACKs received:
0 1

2 lost

timeout
```

Sender may retransmit:

```text
2 3
```

This is why it is called:

> **Go-Back-N**

---

# 65. GBN Receiver

If the receiver gets the expected packet correctly:

```text
accept
deliver to application
send ACK
```

If it gets an out-of-order packet:

```text
discard it
send ACK for most recently received in-order packet
```

The GBN receiver does not normally buffer out-of-order packets in the basic protocol described here.

---

# 66. Why Does GBN Discard Out-of-Order Packets?

Suppose:

```text
Expected: packet 2
Received: packet 3
```

Packet 2 may have been lost.

GBN will eventually retransmit packet 2 and packet 3.

Therefore the receiver can simply discard packet 3.

Advantage:

```text
simple receiver
less buffering
```

Disadvantage:

```text
correctly received packets may be retransmitted unnecessarily
```

---

# 67. GBN Example

Suppose sender sends:

```text
0 1 2 3
```

Packet 2 is lost.

Receiver gets:

```text
0
1
3
```

For packet 3:

```text
out of order
```

Receiver discards packet 3 and sends a cumulative ACK for packet 1.

Sender eventually times out and retransmits:

```text
2
3
```

---

# 68. Selective Repeat — SR

Selective Repeat is designed to avoid unnecessary retransmissions.

Instead of retransmitting:

```text
lost packet
+
all packets after it
```

the sender retransmits:

```text
only the packets that actually need retransmission
```

---

# 69. Selective Repeat Receiver

The receiver individually acknowledges correctly received packets.

It can buffer out-of-order packets.

Example:

```text
Expected 2

Receive 3
```

Instead of discarding 3, SR can:

```text
buffer packet 3
ACK 3
```

When packet 2 arrives:

```text
deliver 2
then deliver buffered 3
```

---

# 70. GBN vs Selective Repeat

| Feature | Go-Back-N | Selective Repeat |
|---|---|---|
| ACK style | Cumulative | Individual |
| Out-of-order packet | Discard | Can buffer |
| Retransmission | From missing/lost packet onward | Only missing/corrupted packet |
| Receiver complexity | Lower | Higher |
| Buffering | Less | More |
| Unnecessary retransmissions | More | Fewer |

---

# 71. Example — GBN vs SR

Suppose:

# 72. Why Pipelining Needs Sequence Numbers

With one packet in flight:

```text
0 / 1
```

may be sufficient.

With multiple packets in flight:

```text
0 1 2 3 4 ...
```

the receiver needs to distinguish each packet.

Therefore:

```text
pipelining
    ↓
multiple outstanding packets
    ↓
unique sequence numbers
```

With Selective Repeat, packet 3 can be stored.


may be required.

# 76. Why Timer Is Necessary

The sender cannot wait forever.

If:

```text

```

```text

```


# 77. Why Timeout Does Not Prove Packet Loss

Important conceptual point:

A timeout only means:

```text
ACK did not arrive before timer expired.
```

Possible causes include:

```text
packet lost
ACK lost
packet delayed
ACK delayed
```

Therefore retransmission is based on a timeout inference, not direct knowledge.

Retransmission can create duplicates.

```text
Sender timeout
Sender retransmits
```

Receiver sees:

```text

```

Therefore:

```text
duplicate
```

and does not deliver the data again.

# 79. ACK Loss vs Packet Loss

### Packet loss

```text
Sender → packet → X
```

Receiver never gets packet.

Sender eventually:

```text

```

### ACK loss

```text
Sender → packet → Receiver

```

Sender times out and retransmits.

Receiver recognizes duplicate using sequence number.

# 88. Why High RTT Is Bad for Stop-and-Wait

If:

```text
RTT ↑
```

while:

```text
L/R
```

stays small, then:

```text
U_sender ↓
```

because the sender spends more time waiting for ACKs.

Therefore long-distance/high-latency paths expose stop-and-wait's weakness.

# 89. Why High Transmission Rate Can Also Hurt Utilization

Suppose:

```text
R ↑
```

Then:

```text
L/R ↓
```

The sender can push the packet into the link even faster.

But the propagation/RTT component may remain almost unchanged.

Therefore:

```text
very fast link
+
large RTT
+
stop-and-wait
=
very poor utilization
```

This is exactly the high-speed-network problem emphasized in the study material.

# 90. Sender Utilization Intuition

Think of:

```text
Utilization =
busy time / total cycle time
```

For stop-and-wait:

```text
busy time = transmission time
total time ≈ transmission time + RTT
```

Therefore:

```text
U =
busy / busy + waiting
```

If waiting dominates:

```text
U → very small
```

# 97. Common MCQ Traps

## Trap 1

rdt2.0 handles packet loss.

**False.**

It handles bit errors under the assumed no-loss channel.

---

## Trap 2

rdt3.0 needs sequence numbers.

**True.**

They are required to handle duplicates caused by retransmissions.

---

## Trap 3

A checksum corrects corrupted packets.

**False.**

Checksum detects corruption.

---

## Trap 4

An ACK proves the packet cannot have been duplicated.

**False.**

Sequence numbers are used to detect duplicates.

---

## Trap 5

A timeout proves the packet was lost.

**False.**

It only indicates that the expected ACK was not received within the timeout interval.

---

## Trap 6

rdt2.2 uses NAK packets.

**False.**

It is NAK-free and uses duplicate ACKs.

---

## Trap 7

GBN retransmits only the lost packet.

**False.**

GBN retransmits from the missing/lost packet onward among outstanding packets.

---

## Trap 8

Selective Repeat retransmits every outstanding packet after a loss.

**False.**

It retransmits only packets that need retransmission.

---

## Trap 9

GBN receiver normally buffers all out-of-order packets.

**False.**

Basic GBN discards out-of-order packets.

---

## Trap 10

Selective Repeat can buffer out-of-order packets.

**True.**

That is one of its major differences from GBN.

---

## Trap 11

Pipelining reduces the number of packets that can be in flight.

**False.**

Pipelining increases the number of packets that can be in flight.

---

## Trap 12

Pipelining removes the need for sequence numbers.

**False.**

It increases the need for sequence-number space.

---

## Trap 13

Stop-and-wait always gives high link utilization.

**False.**

It can be extremely inefficient when RTT is large.

---

## Trap 14

rdt3.0 is incorrect.

**False.**

It is functionally correct but can have poor performance because it is stop-and-wait.

---

## Trap 15

GBN and SR have the same receiver behavior.

**False.**

GBN discards out-of-order packets; SR can buffer them.

# 98. Important Terminology

### ACK

Acknowledgment that a packet was correctly received.

### NAK

Negative acknowledgment indicating corruption in protocols that use explicit NAKs.

### Sequence number

Identifier used to distinguish packets and detect duplicates/order.

### Retransmission

Sending a packet again after suspected loss/corruption.

### Timeout

Expiration of the sender's timer because the expected ACK did not arrive.

### Stop-and-wait

Send one packet, then wait for feedback before sending the next.

### Pipelining

Allow multiple packets to be in flight simultaneously.

### Cumulative ACK

Acknowledgment that implicitly confirms receipt of a sequence of packets up through a particular point.

### Go-Back-N

Pipelined protocol that retransmits from the missing/lost packet onward.

### Selective Repeat

Pipelined protocol that retransmits only packets requiring retransmission.
