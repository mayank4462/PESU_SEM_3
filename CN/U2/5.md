# 2. Socket Programming — Definition

A **socket** is the interface between an application process and the transport layer.

The slide on **page 4** explicitly describes the socket as the:

> **door between application process and end-to-end transport protocol**

Think of a process as a house and its socket as the door.

```text
             APPLICATION PROCESS
                    |
                 SOCKET
                    |
              TRANSPORT LAYER
                    |
                 INTERNET
```

The application sends data into the socket and receives data from the socket.

---

# 3. What Does the Socket Hide?

The application does not need to know the detailed physical path taken by the data.

For example:

```text
Application
    ↓
Socket
    ↓
TCP/UDP
    ↓
IP
    ↓
Routers
    ↓
Destination host
    ↓
TCP/UDP
    ↓
Socket
    ↓
Application
```

The socket provides the application with a simple communication interface.

The underlying operating system and protocol stack handle the lower-level networking details.

# 4. Destination Address

When an application sends data to another process, the destination needs to be identified.

The destination address contains:

```text
Destination IP address
+
Destination port number
```

### IP address

Identifies the destination **host**.

### Port number

Identifies the destination **socket/application endpoint** on that host.

### Memory trick

```text
IP   → Which machine?
Port → Which application/socket?
```

The Highlight Study Notes emphasize that the destination host's IP address allows routers to route the packet toward the destination host.

---

# 5. Source Address

The source side also has addressing information.

Conceptually:

```text
Source IP
Source port
```

The study notes point out an important implementation detail:

> The source address/port information is typically handled automatically by the underlying operating system rather than being manually attached by the UDP application code.

This matters when understanding why a UDP program can receive a sender address from `recvfrom()`.

# 6. Two Main Types of Sockets

The slide on **page 5** identifies two major socket types:

### UDP

```text
UDP → unreliable datagram
```

### TCP

```text
TCP → reliable, byte-stream oriented
```

These two socket types provide different transport services.

---

# 7. UDP Socket

UDP is:

- connectionless
- unreliable
- datagram-oriented
- low overhead

There is no TCP-style connection establishment before data is sent.

Each UDP message is sent as an independent datagram.

---

# 8. TCP Socket

TCP is:

- connection-oriented
- reliable
- byte-stream oriented
- full-duplex

Before normal application data transfer, TCP establishes a connection.

TCP guarantees that the receiving application gets the bytes in the order they were sent.

---

# 9. UDP vs TCP — Core Comparison

| Feature | UDP | TCP |
|---|---|---|
| Connection | No | Yes |
| Data model | Datagram | Byte stream |
| Reliability | No guarantee | Reliable |
| Ordering | No guarantee | In-order |
| Connection setup | No | Yes |
| Retransmission | No built-in | Yes |
| Flow control | No built-in | Yes |
| Congestion control | No built-in | Yes |
| Overhead | Lower | Higher |
| Typical socket type | `SOCK_DGRAM` | `SOCK_STREAM` |

### Exam memory

```text
UDP → datagrams
TCP → byte stream
```


- no connection establishment
- no ongoing connection state

# 12. UDP Application View

From the application's point of view:

> UDP provides an unreliable transfer of groups of bytes called datagrams between the client and server.

Therefore a UDP application must tolerate the possibility that transmitted data:

- may be lost
- may arrive out of order

UDP itself does not fix these problems.

In the basic UDP client example, the client does not explicitly choose a local port.

Instead:

> The operating system automatically assigns an available client-side port when the UDP socket is used.

This is different from the server, which normally needs a known port so clients know where to send their datagrams.

# 16. UDP `recvfrom()`

A UDP receiver can use:


`recvfrom()` returns two important pieces of information:

```text

+
source address
```

The source address contains:

```text
source IP
source port
```

This is why `recvfrom()` is useful for UDP servers.

# 21. UDP Server — Python

```python
from socket import *

serverPort = 12000

serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', serverPort))

print('The server is ready to receive')

while True:
    message, clientAddress = serverSocket.recvfrom(2048)

    modifiedMessage = message.decode().upper()

    serverSocket.sendto(
        modifiedMessage.encode(),
        clientAddress
    )
```

# 26. TCP Socket Programming

The slide on **page 10** introduces TCP socket programming.

TCP is connection-oriented.

Therefore the client and server must first establish a TCP connection.

The basic process:

```text
Client                         Server

Create TCP socket              Create welcoming socket
       |                               |
       | ---- connection request ----> |
       |                               |
       | <---- TCP connection -------- |
       |                               |
       | ===== data exchange =====     |
```

---

# 27. TCP Client — Main Idea

The client:

1. creates a TCP socket
2. specifies the server IP/hostname
3. specifies the server port
4. calls `connect()`
5. TCP performs the connection establishment
6. client sends/receives data
7. closes the connection

---

# 28. TCP Server — Main Idea

The server:

1. creates a welcoming socket
2. binds it to a known port
3. listens for incoming connections
4. accepts a connection
5. receives a new connection socket
6. communicates through that connection socket
7. closes the connection socket after communication

### Important

The welcoming socket is NOT the socket used for ordinary data exchange with one client.

---

# 29. TCP Welcoming Socket

The study notes and slide deck emphasize this distinction.

The server initially creates:

```text
serverSocket
```

This is the **welcoming socket**.

Its job is:

> Wait for incoming connection requests.

Think:

```text
Welcoming socket
=
"Knock here if you want to connect."
```

---

# 30. TCP Connection Socket

When a client connects, the server creates a new socket:

```text
connectionSocket
```

This socket is dedicated to that particular client.

Therefore:

```text
Welcoming socket
       |
       +── Client A → connectionSocket A
       |
       +── Client B → connectionSocket B
       |
       +── Client C → connectionSocket C
```

The welcoming socket remains available to accept additional clients.

---

# 31. The Server Has Two Socket Roles

Very important:

```text
TCP SERVER
    |
    ├── Welcoming socket
    |       ↓
    |   accepts connections
    |
    └── Connection socket
            ↓
       communicates with
       one particular client
```

### MCQ

Which socket receives application data from a connected TCP client?

**Connection socket.**

Not the welcoming socket.

---

# 32. TCP Three-Way Handshake

Before application data transfer:

```text
Client                         Server

   SYN ---------------------->

       <---------------- SYNACK

   ACK ---------------------->
```

The three-way handshake is performed by the transport layer.

The application program does not manually implement the SYN/SYNACK/ACK exchange.

---

# 33. What Happens During the Handshake?

## Step 1

Client sends:

```text
SYN
```

It includes the client's initial sequence number.

## Step 2

Server sends:

```text
SYN + ACK
```

It acknowledges the client and provides its own initial sequence number.

## Step 3

Client sends:

```text
ACK
```

Now the TCP connection is established.

### Memory

```text
SYN → SYNACK → ACK
```

# 36. TCP Server — Python

A simplified TCP server follows:

```python
from socket import *

serverPort = 12000

serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))
serverSocket.listen(1)

print('The server is ready to receive')

while True:
    connectionSocket, clientAddress = serverSocket.accept()

    sentence = connectionSocket.recv(1024)

    capitalizedSentence = sentence.decode().upper()

    connectionSocket.send(capitalizedSentence.encode())

    connectionSocket.close()
```

# 38. `accept()` — Extremely Important

`accept()` is used by the TCP server to accept a connection.

It produces a **new connection socket**.

Conceptually:

```text
serverSocket
     |
   accept()
     |
     ↓
connectionSocket
```

The original:

```text
serverSocket
```

continues serving as the welcoming/listening socket.

# 39. TCP Data Exchange

After `accept()`:

```text
Client socket
      ||
      || TCP connection
      ||
Connection socket
```

The client can:

```text
send()
recv()
```

The server can:

```text
recv()
send()
```

Both directions are possible because TCP is full-duplex.

# 40. TCP Server — Why Connection Socket?

Suppose three clients connect:

```text
                 serverSocket
                     |
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Client A     Client B     Client C
        ↓            ↓            ↓
   connSocket A  connSocket B  connSocket C
```

Each client gets a dedicated server-side connection socket.

This allows the server to maintain separate communication state for each client.

# 43. UDP Socket vs TCP Socket

## UDP socket

The application sends each datagram with a destination address.

```text
sendto(message, destination)
```

The receiver gets the sender's address with:

```text
recvfrom()
```

There is no connection state.

---

## TCP socket

The client first establishes a connection.

```text
connect()
```

The server accepts it.

```text
accept()
```

Then data flows through the established connection.

---

# 44. TCP Connection as a Pipe

The Highlight Study Notes use the useful analogy:

> From the application's perspective, the client socket and server connection socket behave like a pipe.

```text
Client process
     |
Client socket
     ||
     || TCP connection
     ||
Connection socket
     |
Server process
```

The client can send bytes into the socket.

TCP guarantees that the server receives the bytes in order.

The server can also send bytes back.

Therefore TCP communication is full-duplex.

---

# 45. TCP Reliable Byte Stream

TCP provides:

```text
Reliable
+
In-order
+
Byte-stream
```

If the client sends:

```text
A B C D E
```

the receiving application gets the bytes in the same order.

TCP handles the underlying reliability mechanisms.

The application does not manually retransmit every lost segment.

---

# 46. UDP Datagram vs TCP Byte Stream

This is a very important conceptual difference.

## UDP

Preserves message/datagram boundaries.

Example:

```text
send("ABC")
send("DEF")
```

The receiver receives separate datagrams.

## TCP

Provides a byte stream.

Example:

```text
send("ABC")
send("DEF")
```

TCP presents a continuous stream of bytes:

```text
ABCDEF
```

The application should not assume that one `send()` corresponds to one `recv()`.

### MCQ trap

> TCP is message-oriented.

❌ False in the standard Kurose socket model.

TCP is **byte-stream oriented**.

---

# 47. TCP Does Not Preserve Application Message Boundaries

Suppose:

```text
Sender:
send("HELLO")
send("WORLD")
```

The receiver may read:

```text
HELLOWORLD
```

or portions of the stream depending on how data is buffered/read.

Therefore the application needs its own message framing if it needs explicit message boundaries.

---

# 48. UDP Preserves Datagram Boundaries

UDP treats each message as an individual datagram.

Conceptually:

```text
Datagram 1
Datagram 2
Datagram 3
```

Each can be independently sent/received.

This is one reason UDP is called **datagram-oriented**.

# 67. UDP Header Size

The UDP header is:

```text
8 bytes
```

It consists of four fields, each:

```text
16 bits = 2 bytes
```

Therefore:

```text
4 × 2 bytes = 8 bytes
```

or:

```text
4 × 16 bits = 64 bits = 8 bytes
```

---

# 68. UDP Length Field

The UDP **length field** indicates the length of the **entire UDP segment/datagram**.

It includes:

```text
UDP header
+
UDP payload
```

### Important MCQ trap

It does **not** represent only the application data.

---

# 69. Why Is UDP Length in Bytes?

The length field is expressed in **bytes**.

For example:

```text
UDP header = 8 bytes
Payload = 100 bytes

UDP length = 108 bytes
```

Therefore:

```text
UDP length ≠ payload length only
```

---

# 70. UDP Checksum

The checksum is used to detect errors in the UDP segment.

Conceptually:

```text
Sender
  ↓
Calculate checksum
  ↓
Transmit
  ↓
Receiver
  ↓
Recalculate/check
  ↓
Compare
```

If the values indicate inconsistency, corruption may have occurred.

---

# 71. Why One's Complement?

The slide asks:

> Why transmit the complement rather than the sum itself?

The reason is that the receiver can include the transmitted checksum in the same one's-complement addition.

For correct data, the resulting value has the expected all-ones pattern.

This lets the receiver test integrity using the same addition mechanism rather than needing a separate subtraction operation.

---

# 72. UDP Checksum — Exam-Level Procedure

Conceptually:

### Sender

1. Divide checksum input into 16-bit words.
2. Add them using one's-complement arithmetic.
3. Take the one's complement of the result.
4. Place that value in the checksum field.

### Receiver

1. Adds the received 16-bit words, including the checksum.
2. Uses one's-complement addition.
3. Checks the resulting pattern.

The expected correct result is:

```text
all 1s
```

under the standard checksum interpretation.

---

# 73. UDP Checksum vs Reliability

Very important:

```text
Checksum
    ↓
Error detection
```

It does NOT provide:

```text
Retransmission
Ordering
Delivery guarantee
Duplicate elimination
```

Therefore:

> **UDP checksum does not make UDP reliable.**

# 74. Study Notes — Transport-Layer Context

The Highlight Study Notes explain that the transport layer:

1. receives application-layer messages
2. creates transport-layer segments
3. may break application messages into smaller pieces
4. adds transport-layer header information
5. passes segments to the network layer

At the receiver:

```text
Network layer
      ↓
Transport segment
      ↓
Transport layer
      ↓
Application process
```

The transport layer makes the received data available to the application.

---

# 75. Routers vs Transport Layer

A useful conceptual point from the study material:

Routers operate primarily on **network-layer fields**.

They do not normally process the application data or make application-level decisions about the contents of the transport payload.

Conceptually:

```text
Router:
IP/network header → routing decision

Destination host:
transport header → socket/process delivery
```

# 76. TCP Reliability Behind the Socket API

When the application uses:

```python
connectionSocket.send(...)
```

the application does not manually perform:

- sequence numbering
- acknowledgments
- retransmission
- timeout handling
- ordering

TCP handles these transport-layer functions.

The application sees a reliable ordered byte stream.

---

# 77. TCP Flow Control Behind the Socket API

TCP also protects the receiver from being overwhelmed.

The receiver advertises available buffer space through TCP flow-control mechanisms.

The application does not manually implement this for ordinary TCP sockets.

---

# 78. TCP Congestion Control Behind the Socket API

TCP also regulates its sending rate according to network congestion.

Again, this happens inside the transport layer.

The application simply uses the socket interface.

# 84. Final Mental Model

If a question gives you a networking program, think in this order:

```text
1. TCP or UDP?
        ↓
2. What socket type?
        ↓
3. Is connection setup required?
        ↓
4. What operation sends data?
        ↓
5. What operation receives data?
        ↓
6. Does server need bind?
        ↓
7. Does server need listen/accept?
        ↓

        ↓
```

```text

socket → bind(server) → sendto/recvfrom

socket → bind(server) → listen → accept
client: socket → connect
then: send/recv
```

This is the core pattern behind essentially every socket-programming MCQ in this slide set.
