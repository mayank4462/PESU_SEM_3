# 2. What Does the Transport Layer Do?

## 2.1 Basic idea

The **network layer** provides communication between **hosts**.

The **transport layer** extends this to communication between **processes** running on those hosts.

### Remember

> **Network layer → host-to-host**
>
> **Transport layer → process-to-process**

Example:

Your laptop may simultaneously run:

- Chrome
- WhatsApp
- Zoom
- SSH

All of them use the same network connection, but their data must reach the correct application process.

The transport layer handles this process-to-process delivery.

---

# 3. Logical End-to-End Communication

The slide on page 5 shows **logical end-to-end transport**.

Imagine:

```text
Application process
        ↓
Transport layer
        ↓
Network
        ↓
Transport layer
        ↓
Application process
```

The transport layer makes the two application processes behave as if they have a direct logical communication channel.

Physically, packets still pass through routers and multiple networks.

### Important distinction

**Logical communication does NOT mean there is a physical direct connection.**

It means the transport layer provides the abstraction of process-to-process communication.

---

# 4. What Does the Transport Layer Receive and Produce?

At the sender:

```text
Application message
        ↓
Transport layer
        ↓
Transport segment
        ↓
Network layer
```

The transport layer:

- receives an application-layer message
- breaks it into transport segments if necessary
- adds a transport-layer header
- passes the segment to the network layer

At the receiver:

```text
Network layer
      ↓
Transport segment
      ↓
Transport layer
      ↓
Application message
```

The transport layer:

- receives segments from IP/network layer
- checks the transport header
- extracts application data
- performs demultiplexing
- delivers the data to the correct socket/application process

# 6. Transport-Layer Services

The transport layer can provide different services depending on the protocol.

The two major Internet transport protocols are:

- **TCP — Transmission Control Protocol**
- **UDP — User Datagram Protocol**

---

# 7. TCP Services

TCP provides:

- reliable data delivery
- in-order delivery
- connection-oriented communication
- flow control
- congestion control
- retransmission of lost data
- acknowledgments
- sequence numbers
- timers

### Slide summary

TCP provides:

> **reliable, in-order delivery**

plus:

> **congestion control**
>
> **flow control**
>
> **connection setup**

---

# 8. UDP Services

UDP provides:

- process-to-process delivery
- error detection using checksum
- connectionless communication

UDP does **not** guarantee:

- reliable delivery
- in-order delivery
- retransmission
- flow control
- congestion control

### Important

UDP is not "bad" or "broken".

It deliberately provides a minimal service with low overhead.

The application can implement additional reliability itself if needed.

---

# 9. TCP vs UDP — Core Comparison

| Feature | TCP | UDP |
|---|---|---|
| Connection | Connection-oriented | Connectionless |
| Reliable delivery | Yes | No |
| Ordered delivery | Yes | No guarantee |
| ACKs | Yes | No |
| Retransmission | Yes | No |
| Sequence numbers | Yes | No |
| Flow control | Yes | No |
| Congestion control | Yes | No |
| Checksum/error detection | Yes | Yes |
| Handshake | Yes | No |
| Overhead | Higher | Lower |
| Typical use | Web, file transfer, reliable applications | DNS, streaming/real-time applications, applications needing low overhead |

### MCQ trap

> UDP having a checksum does **NOT** mean UDP provides reliable delivery.

Checksum detects corruption.

It does not guarantee delivery or retransmission.

# 10. Flow Control vs Congestion Control

These are commonly confused.

## Flow control

Protects the **receiver**.

Problem:

> Sender is sending faster than receiver can process/store.

TCP uses the receiver's advertised window (`rwnd`) to prevent receiver-buffer overflow.

### Think:

**Flow control = receiver protection**

---

## Congestion control

Protects the **network**.

Problem:

> Too much traffic is being injected into the network, causing congestion.

TCP regulates its sending rate according to network conditions.

### Think:

**Congestion control = network protection**

---

# 11. UDP Is Unreliable — What Exactly Does That Mean?

"Unreliable" means UDP does not guarantee:

- segment delivery
- ordering
- duplicate prevention
- retransmission
- recovery from loss

A UDP segment may:

- arrive
- arrive late
- arrive out of order
- be duplicated
- be corrupted and detected by checksum
- never arrive

UDP simply does not provide mechanisms to fix these problems.

# 12. Socket Programming

## 12.1 What is a socket?

A **socket** is the interface between:

```text
Application process
        ↕
      Socket
        ↕
Transport layer
```

Kurose & Ross describes the socket as a **door** through which data passes between the application and network.

### Simple definition

> A socket is an endpoint/interface through which an application process communicates with the transport layer.

---

# 13. IP Address vs Port Number

Two different things identify communication endpoints.

## IP address

Identifies the **host**.

Example:

```text
192.168.1.20
```

## Port number

Identifies the **application endpoint/process/socket** on that host.

Example:

```text
192.168.1.20 : 80
```

means:

- host = `192.168.1.20`
- application endpoint = port `80`

### Memory trick

> **IP → Which computer?**
>
> **Port → Which application?**

---

# 14. Port Numbers

Port numbers are **16-bit**.

Range:

```text
0 – 65535
```

Ports:

```text
0–1023 → well-known ports
```

Examples:

| Application | Port |
|---|---:|
| HTTP | 80 |
| HTTPS | 443 |
| FTP control | 21 |
| SSH | 22 |
| Telnet | 23 |
| SMTP | 25 |
| DNS | 53 |

### MCQ trap

A port number does **not** identify the physical computer.

The IP address identifies the host.

---

# 15. Multiplexing

## Definition

At the sender, data from multiple application sockets is collected and passed to the transport layer.

```text
Chrome socket ─┐
Zoom socket ───┼──→ Transport layer → segments
SSH socket ────┘
```

This is **multiplexing**.

### Remember

> **Multiplexing = many → one transport output**

---

# 16. Demultiplexing

At the receiver, incoming transport segments are delivered to the correct socket.

```text
Incoming segments
       ↓
Transport layer
   ↙    ↓     ↘
Chrome Zoom   SSH
```

This is **demultiplexing**.

### Remember

> **Demultiplexing = one incoming stream → correct socket**

---

# 17. Multiplexing vs Demultiplexing

| Sender | Receiver |
|---|---|
| Multiplexing | Demultiplexing |
| Combines data from sockets | Separates incoming data |
| Many sockets → transport | Transport → correct socket |

### Very common MCQ

**Multiplexing occurs at the sender.**

**Demultiplexing occurs at the receiver.**

---

# 18. How Demultiplexing Knows Where to Send Data

Transport-layer segments contain addressing information such as:

- source port number
- destination port number

The transport layer examines this information and determines the appropriate socket.

For UDP, the destination port is especially important for identifying the receiving socket.

For TCP, connection identification uses the TCP connection's addressing information.

# 19. UDP Socket Programming

A Python UDP socket can be created using:

```python
clientSocket = socket(AF_INET, SOCK_DGRAM)
```

Meaning:

- `AF_INET` → IPv4
- `SOCK_DGRAM` → UDP datagram socket

A socket can be bound to a port:

```python
clientSocket.bind(('', 19157))
```

This associates the socket with port `19157` on the local host.

# 20. UDP Communication

Typical UDP flow:

```text
Application
    ↓
UDP socket
    ↓
UDP segment
    ↓
IP
    ↓
Network
    ↓
IP
    ↓
UDP
    ↓
Destination socket
    ↓
Application
```

UDP does not first establish a connection.

The sender can send a datagram directly.

---

# 21. UDP `sendto()` and `recvfrom()`

UDP commonly uses:

```python
sendto()
```

to send data.

The sender specifies the destination address and port.

The receiver commonly uses:

```python
recvfrom()
```

to receive data and identify where it came from.

### Key idea

UDP is connectionless, so there is no TCP-style connection establishment before sending.

---

# 22. UDP Checksum

The UDP checksum is used for **error detection**.

The receiver uses the checksum to determine whether the segment's contents have been corrupted.

### Important distinction

```text
Checksum → detects corruption
Retransmission → recovers from loss/corruption
```

UDP provides the first but not the second.

Therefore:

> **UDP checksum ≠ reliable transport**

# 23. Principles of Reliable Data Transfer

This is one of the most important topics in the study notes.

A reliable data-transfer protocol must handle problems such as:

- corrupted packets
- lost packets
- duplicate packets
- packets arriving out of order

The general mechanisms include:

- acknowledgments
- sequence numbers
- retransmissions
- timers

---

# 24. ACK — Acknowledgment

An **ACK** tells the sender that data has been successfully received.

Example:

```text
Sender ───── Data ─────→ Receiver
Sender ←──── ACK ─────── Receiver
```

If the sender receives the expected ACK, it can continue.

If the ACK does not arrive, the sender may assume the segment was lost and retransmit.

---

# 25. Sequence Numbers

Sequence numbers help the receiver:

- identify data
- detect duplicates
- detect missing data
- reorder data
- identify which data has been acknowledged

Without sequence numbers, retransmission could cause the receiver to accept the same data twice.

---

# 26. Retransmission

Suppose:

```text
Sender ─── Segment 1 ───→ X
```

The segment is lost.

The sender waits for an ACK.

No ACK arrives.

The sender retransmits:

```text
Sender ─── Segment 1 ───→ Receiver
Sender ←──── ACK ───────── Receiver
```

Retransmission is one of the fundamental mechanisms used for reliable data transfer.

---

# 27. Timers

The sender starts a timer after transmitting data.

If the expected ACK does not arrive before the timer expires:

```text
Timeout
   ↓
Retransmit
```

### Important

The timeout must not be:

- too short → unnecessary retransmissions
- too long → slow recovery from loss

TCP therefore estimates the round-trip time.

---

# 28. Stop-and-Wait Reliable Data Transfer

In **Stop-and-Wait**, the sender:

1. sends one packet
2. waits for ACK
3. sends the next packet only after ACK arrives

```text
Send 1
  ↓
Wait
  ↓
ACK
  ↓
Send 2
  ↓
Wait
```

### Problem

The sender may spend a lot of time waiting.

Therefore, the link can be underutilized, especially when the RTT is large.

---

# 29. Why Stop-and-Wait Can Be Slow

Suppose:

- packet transmission is very fast
- propagation/RTT is large

Then:

```text
Send → WAIT → WAIT → ACK → Send next
```

The sender spends most of its time waiting.

This is inefficient.

---

# 30. Pipelined Reliable Data Transfer

Pipelining solves the Stop-and-Wait efficiency problem.

Instead of allowing only one unacknowledged packet:

```text
Packet 1 → Packet 2 → Packet 3 → Packet 4
```

multiple packets can be in flight at the same time.

### Benefit

The link can remain busy while acknowledgments are travelling back.

### Core idea

> **Pipelining = multiple unacknowledged packets in flight**

---

# 31. Go-Back-N (GBN)

GBN is a pipelined reliable-data-transfer protocol.

It uses **cumulative acknowledgments**.

If the receiver receives packets:

```text
1
2
3
4
```

an ACK can indicate that all data up to a particular point has been received.

### If a packet is lost

Suppose:

```text
1 ✓
2 ✓
3 LOST
4 arrives
5 arrives
```

The sender may need to retransmit packet 3 and the later packets that depend on it.

Hence:

> **Go-Back-N → retransmit from the missing packet onward**

---

# 32. Selective Repeat (SR)

Selective Repeat is also pipelined.

But it is more selective.

Suppose:

```text
1 ✓
2 ✓
3 LOST
4 ✓
5 ✓
```

SR can keep correctly received packets 4 and 5 and retransmit only packet 3.

### Remember

| GBN | Selective Repeat |
|---|---|
| Cumulative ACKs | Individual/selective ACK behavior |
| Retransmits missing packet and later affected packets | Retransmits only missing packets |
| Less selective | More selective |

### MCQ trap

> **Selective Repeat does NOT retransmit every packet after a lost packet.**

---

# 33. TCP Connection

TCP is **connection-oriented**.

Before application data is exchanged, TCP establishes a connection between the two endpoints.

A TCP connection provides:

- full-duplex data transfer
- reliable delivery
- ordered delivery
- flow control
- congestion control

### Full-duplex

Both sides can send data simultaneously.

```text
A  ←────────→  B
```

---

# 34. TCP Segment Structure

A TCP segment contains:

```text
TCP Header
    +
Application Data
```

Important TCP header information includes:

- source port
- destination port
- sequence number
- acknowledgment number
- flags
- receive window
- checksum

The study notes also emphasize:

- TCP buffers
- MSS
- MTU
- header fields

---

# 35. MSS — Maximum Segment Size

MSS is the maximum amount of application data that TCP places in a single segment.

Think:

```text
TCP segment
┌────────────────────────────┐
│ TCP Header │ Application   │
│            │ Data ≤ MSS    │
└────────────────────────────┘
```

MSS is related to the underlying network's packet-size constraints.

---

# 36. MTU — Maximum Transmission Unit

MTU is the maximum size of an IP packet that can be transmitted over a particular link without fragmentation.

### MSS vs MTU

> **MTU → IP packet size**
>
> **MSS → TCP application-data size**

Do not confuse them.

---

# 37. TCP Sequence Numbers

TCP sequence numbers are based on **bytes**, not simply "packet numbers."

Example:

If the first byte of data has sequence number 1000 and the segment contains 500 bytes:

```text
Sequence number = 1000
Next expected byte = 1500
```

The sequence number identifies the position of the first byte in the segment.

---

# 38. TCP Acknowledgments

TCP uses acknowledgments to indicate received data.

TCP ACKs are generally **cumulative**.

If the receiver sends:

```text
ACK = 1500
```

it means the receiver is expecting byte 1500 next.

Thus bytes before 1500 have been received successfully in order.

---

# 39. Duplicate ACKs

A duplicate ACK can indicate that the receiver is still waiting for a particular missing byte/segment.

Example:

```text
1 arrives
2 LOST
3 arrives
```

The receiver cannot deliver 3 in order if 2 is missing.

It may generate duplicate ACKs for the same expected byte.

TCP can use duplicate ACKs as an indication of possible loss.

---

# 40. TCP RTT

RTT = **Round-Trip Time**

It is approximately:

```text
time for data/segment to travel to receiver
+
time for acknowledgment to return
```

TCP estimates RTT to determine an appropriate retransmission timeout.

---

# 41. TCP Timeout

If:

```text
Timer expires
```

before the expected ACK arrives:

```text
Possible loss
      ↓
Retransmit
```

### Why not use a fixed tiny timeout?

Because network delay changes.

A timeout that is too short causes unnecessary retransmissions.

A timeout that is too long causes slow recovery.

Therefore TCP estimates RTT dynamically.

---

# 42. TCP Reliable Data Transfer

TCP combines:

- sequence numbers
- ACKs
- retransmission
- timers
- checksum
- buffering

to provide reliable ordered delivery.

### Simplified flow

```text
Sender
  |
  | Segment + sequence number
  ↓
Network
  |
  ↓
Receiver
  |
  | ACK
  ↓
Sender
```

If data is lost:

```text
Timeout / duplicate ACKs
          ↓
      Retransmission
```

---

# 43. TCP Flow Control

The receiver has a buffer.

If the sender sends too much data too quickly, the receiver's buffer could overflow.

TCP therefore uses a **receive window (`rwnd`)**.

The receiver tells the sender how much additional data it can accept.

A key relationship from the study notes is:

```text
LastByteSent − LastByteAcked ≤ rwnd
```

This limits the amount of unacknowledged data that the sender can have outstanding based on receiver capacity.

### Remember

> `rwnd` → receiver's available buffer space

---

# 44. TCP Congestion Control

TCP also regulates the amount of traffic entering the network.

This protects:

- routers
- links
- the network as a whole

The sender adjusts its sending behavior based on network congestion.

### Important distinction

```text
Flow control → receiver
Congestion control → network
```

---

# 45. TCP Three-Way Handshake

This is extremely important for MCQs.

TCP connection establishment:

```text
Client                         Server

   SYN ───────────────────────→

       ←──────────────── SYNACK

   ACK ───────────────────────→
```

Three steps:

### Step 1 — SYN

Client sends a TCP segment with:

```text
SYN = 1
```

It contains the client's initial sequence number.

---

### Step 2 — SYNACK

Server responds with:

```text
SYN = 1
ACK = 1
```

The server:

- acknowledges the client's SYN
- provides its own initial sequence number

---

### Step 3 — ACK

Client sends an ACK acknowledging the server's SYN.

The connection is then established.

---

# 46. Why the Three-Way Handshake?

It allows both endpoints to:

- establish connection state
- exchange initial sequence numbers
- confirm bidirectional communication
- allocate required connection resources

### Memory

```text
SYN
↓
SYN + ACK
↓
ACK
```

---

# 47. TCP Connection — Full Picture

```text
        CONNECTION SETUP
Client ---------------------- Server
        SYN

Client <--------------------- Server
        SYN + ACK

Client ---------------------- Server
        ACK


        DATA TRANSFER

Client =====================> Server
Client <===================== Server
        Full duplex


        CONNECTION STATE
Buffers + sequence numbers + ACKs
+ timers + flow control + congestion control
```

# 51. Case-Based Questions

## Case 1

A laptop is simultaneously running Chrome, Zoom and SSH. Incoming segments must be delivered to the correct application.

### Answer

This is **demultiplexing**.

The transport layer examines addressing information and delivers the data to the appropriate socket.

---

## Case 2

A sender transmits data faster than the receiver can process it.

### Answer

This is a **flow-control** problem.

TCP uses the receive window (`rwnd`) to prevent receiver-buffer overflow.

---

## Case 3

Many users send traffic through the same router and the network becomes overloaded.

### Answer

This is a **congestion-control** problem.

TCP regulates its sending rate to reduce network congestion.

---

## Case 4

A TCP segment is lost.

### Answer

TCP can detect the loss using mechanisms such as:

- timeout
- duplicate ACKs

and retransmit the missing data.

---

## Case 5

A UDP packet is corrupted during transmission.

### Answer

UDP checksum can detect the corruption.

UDP itself does not provide reliable retransmission.

---

## Case 6

A protocol must deliver data quickly and does not require built-in reliability.

### Likely choice

UDP.

But the exact protocol choice depends on the application requirements.

---

## Case 7

An application requires reliable, ordered delivery.

### Likely choice

TCP.

# 52. High-Yield MCQ Traps

### Trap 1

**UDP checksum means UDP is reliable.**

❌ False.

Checksum provides error detection, not reliable delivery.

---

### Trap 2

**Multiplexing happens at receiver.**

❌ False.

Multiplexing → sender.

Demultiplexing → receiver.

---

### Trap 3

**IP identifies the application.**

❌ False.

IP identifies the host.

Port identifies the application endpoint.

---

### Trap 4

**TCP is unidirectional.**

❌ False.

TCP provides full-duplex communication.

---

### Trap 5

**Flow control prevents network congestion.**

❌ False.

Flow control protects the receiver.

Congestion control protects the network.

---

### Trap 6

**TCP sequence numbers count packets.**

❌ False.

TCP sequence numbers identify **bytes**.

---

### Trap 7

**Selective Repeat retransmits every packet after a lost packet.**

❌ False.

That behavior is associated with Go-Back-N.

Selective Repeat retransmits only what is required.

---

### Trap 8

**Stop-and-Wait keeps many packets in flight.**

❌ False.

Stop-and-Wait allows essentially one outstanding packet at a time.

Pipelining allows multiple packets in flight.

---

### Trap 9

**TCP starts sending application data before establishing a connection.**

For normal TCP connection establishment:

❌ No.

The TCP connection is established using the three-way handshake before normal data transfer.

# 55. TCP or UDP? Decision Logic

Ask:

### Does every piece of data need reliable, ordered delivery?

→ TCP-type reliable transport.

### Is low overhead / low latency more important and can the application tolerate loss?

→ UDP-type transport.

### Does the application need built-in retransmission and ordering?

→ TCP.

### Does the application implement its own reliability?

UDP can still be used.

# 60. One-Minute Explanation

> The **transport layer** provides logical **process-to-process communication** over the network. Applications communicate with the transport layer through **sockets**. The **IP address identifies the host**, while the **port number identifies the application endpoint**. At the sender, the transport layer performs **multiplexing**; at the receiver it performs **demultiplexing**. **UDP** is connectionless and provides process-to-process delivery plus checksum-based error detection, but no reliability, ordering, retransmission, flow control, or congestion control. **TCP** is connection-oriented and provides reliable, ordered delivery using sequence numbers, ACKs, retransmissions and timers, along with flow control and congestion control. TCP establishes a connection using **SYN → SYNACK → ACK**. Reliable-data-transfer principles explain ACKs, sequence numbers, timers, Stop-and-Wait, pipelining, Go-Back-N and Selective Repeat.
