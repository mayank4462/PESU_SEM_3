# 1. DNS --- Domain Name System

## 1.1 Why do we need DNS?

A computer communicates using **IP addresses**, for example:

``` text
93.184.216.34
```

Humans do not want to remember IP addresses for every website.

So we use names such as:

``` text
www.example.com
```

DNS provides the mapping:

``` text
Hostname/domain name  →  IP address
```

Example:

``` text
www.example.com → 93.184.216.34
```

### The basic idea

``` text
Human
  |
  | "www.example.com"
  v
DNS
  |
  | "93.184.216.34"
  v
Internet connection to destination
```

### Important exam point

DNS is an **application-layer protocol**.

It is not part of the network layer.

DNS is used by other application-layer protocols such as: - HTTP - SMTP

The study notes also point out that DNS commonly runs over **UDP port
53** for ordinary DNS queries.

------------------------------------------------------------------------

# 2. DNS does more than hostname → IP

A common mistake is to think:

> DNS = converts website name to IP.

That is only the most familiar function.

DNS provides several services.

## 2.1 Hostname-to-IP translation

``` text
www.example.com
        ↓
      DNS
        ↓
IP address
```

This is called **name resolution**.

------------------------------------------------------------------------

## 2.2 Host aliasing

A host can have: - a complicated canonical hostname - one or more easier
aliases

Example:

``` text
Canonical name:
server23.department.example.com

Alias:
www.example.com
```

DNS can map the alias to the canonical hostname.

The relevant record is usually:

``` text
CNAME
```

------------------------------------------------------------------------

## 2.3 Mail server aliasing

DNS can map a domain's mail service to a mail server.

Example:

``` text
example.com
     ↓
MX record
     ↓
mail.example.com
```

The `MX` record tells mail systems which mail server handles mail for a
domain.

------------------------------------------------------------------------

## 2.4 Load distribution

A popular website may run on many servers:

``` text
www.example.com
       |
       +---- IP 1
       +---- IP 2
       +---- IP 3
       +---- IP 4
```

DNS can return multiple IP addresses.

The slide notes explain that DNS can rotate the order of returned
addresses. If clients generally try the first address, this can
distribute requests among replicated servers.

### Remember

``` text
Multiple servers
      ↓
Multiple IP addresses
      ↓
DNS returns addresses
      ↓
Traffic gets distributed
```

------------------------------------------------------------------------

# 3. Why isn't DNS one giant centralized database?

Imagine one DNS server storing every hostname on Earth.

That would create several problems.

## 3.1 Single point of failure

If that one server fails:

``` text
DNS fails
   ↓
Name resolution fails
   ↓
Huge part of Internet becomes difficult/unusable
```

------------------------------------------------------------------------

## 3.2 Traffic concentration

Every DNS request worldwide would have to reach the same server.

That creates an enormous traffic bottleneck.

------------------------------------------------------------------------

## 3.3 Maintenance problem

One server would need records for essentially the whole Internet.

The database would be huge and constantly changing.

------------------------------------------------------------------------

## 3.4 Geographic distance

A single server would be physically far away from many clients.

For example:

``` text
Client in India
      |
      | DNS query
      v
One server in another continent
```

This adds delay.

------------------------------------------------------------------------

## Conclusion

DNS is **distributed and hierarchical**, rather than centralized.

### Memory trick

``` text
DNS is distributed because:
F = Failure
T = Traffic
M = Maintenance
D = Distance

FTMD
```

------------------------------------------------------------------------

# 4. DNS as a distributed hierarchical database

This is one of the most important concepts.

DNS is essentially:

> A **distributed hierarchical database** that stores information about
> domain names.

The DNS namespace is tree-shaped.

Conceptually:

``` text
                         .
                    Root / 
                   /     \
                .com     .org
                 |
              example
                 |
          ┌──────┴──────┐
         www           mail
```

The study notes describe DNS as a distributed database whose information
becomes **more specific as we move downward through the hierarchy**.

------------------------------------------------------------------------

# 5. DNS hierarchy

There are three major server categories you must know:

1.  **Root DNS servers**
2.  **TLD DNS servers**
3.  **Authoritative DNS servers**

And, separately, hosts normally use a:

4.  **Local DNS server / recursive resolver**

------------------------------------------------------------------------

# 6. Root DNS servers

At the top of the hierarchy is the **root**.

Represent it as:

``` text
.
```

The slide deck describes:

-   **13 logical root name servers**
-   these are replicated worldwide
-   there are many physical instances of these logical root servers

### Important distinction

Do NOT say:

> There are only 13 physical root servers.

Better:

> There are 13 logical root server identities, implemented by many
> replicated instances around the world.

------------------------------------------------------------------------

## What does a root server do?

A root server generally does **not** give you the final IP address of:

``` text
www.amazon.com
```

Instead, it points you toward the appropriate **TLD server**.

Example:

``` text
www.amazon.com
       ↓
     Root
       ↓
   .com TLD
       ↓
Authoritative DNS
       ↓
Amazon IP
```

------------------------------------------------------------------------

# 7. TLD servers

TLD = **Top-Level Domain**

Examples:

``` text
.com
.org
.net
.edu
.in
.uk
.jp
```

There are also country-code TLDs.

## What does a TLD server do?

A TLD server knows where to find the authoritative DNS servers
responsible for domains under that TLD.

Example:

``` text
www.amazon.com
      ↓
Root
      ↓
.com TLD
      ↓
Amazon's authoritative DNS
```

The `.com` TLD does not normally hold the final `www.amazon.com → IP`
mapping.

It helps direct the resolver to the authoritative server.

------------------------------------------------------------------------

# 8. Authoritative DNS servers

An **authoritative DNS server** contains DNS records for the domain/zone
for which it has authority.

Example:

``` text
example.com
      |
      +---- authoritative DNS
                |
                +---- www → IP
                +---- mail → server
                +---- aliases
```

For a university/company, its authoritative DNS servers may be operated
by: - the organization itself - a DNS service provider

### Key difference

``` text
Root:
"I know where the .com servers are."

TLD:
"I know where the authoritative servers for example.com are."

Authoritative:
"I have the actual records for example.com."
```

This three-line explanation is worth memorizing.

------------------------------------------------------------------------

# 9. DNS zones vs DNS domains

This is a common conceptual question.

## Domain

A **domain** is a portion of the hierarchical DNS namespace.

Example:

``` text
example.com
```

It may contain:

``` text
www.example.com
mail.example.com
cs.example.com
```

------------------------------------------------------------------------

## Zone

A **zone** is the portion of the DNS namespace for which a particular
administrative authority is responsible.

A domain can be divided into multiple zones.

Example:

``` text
example.com
     |
     +--- www.example.com
     |
     +--- mail.example.com
     |
     +--- cs.example.com
              |
              +--- further delegated zone
```

### Easy distinction

``` text
DOMAIN = namespace/subtree concept

ZONE = administratively managed portion of that namespace
```

### Slide idea

DNS is organized according to zones.

A zone contains the DNS records for the names for which that authority
is responsible.

------------------------------------------------------------------------

# 10. Local DNS server / local resolver

A host normally does not start by contacting a root server directly.

It usually sends its DNS query to a **local DNS server**.

This local server is commonly provided by: - ISP - university -
company - public DNS provider

Examples of public DNS services include:

``` text
8.8.8.8
```

and

``` text
1.1.1.1
```

------------------------------------------------------------------------

## Important: local DNS is not a strict hierarchy level

The local DNS server does not "belong" to the DNS hierarchy in the same
way root/TLD/authoritative servers do.

Instead, it acts as a **resolver/proxy/cache** for clients.

### Flow

``` text
Your computer
     |
     | DNS query
     v
Local DNS resolver
     |
     | if answer is not cached,
     | ask DNS hierarchy
     v
Root / TLD / Authoritative
```

The study notes emphasize that the local DNS server is typically
geographically close to the host.

------------------------------------------------------------------------

# 11. Full DNS lookup --- the big picture

Suppose you type:

``` text
www.amazon.com
```

Your computer needs the IP address.

## Step 1 --- Host asks local DNS server

``` text
Client → Local DNS
```

Question:

``` text
What is the IP address of www.amazon.com?
```

------------------------------------------------------------------------

## Step 2 --- Local DNS checks its cache

If already cached:

``` text
Local DNS → Client
```

Done.

No root/TLD lookup required.

------------------------------------------------------------------------

## Step 3 --- If not cached, resolver contacts root

``` text
Local DNS → Root
```

Root responds approximately:

``` text
Ask the .com TLD server.
```

------------------------------------------------------------------------

## Step 4 --- Ask .com TLD

``` text
Local DNS → .com TLD
```

TLD responds approximately:

``` text
Ask Amazon's authoritative DNS server.
```

------------------------------------------------------------------------

## Step 5 --- Ask authoritative DNS

``` text
Local DNS → Amazon authoritative DNS
```

Authoritative server returns:

``` text
www.amazon.com → IP address
```

------------------------------------------------------------------------

## Step 6 --- Local DNS gives answer to client

``` text
Authoritative
      ↓
Local DNS
      ↓
Client
```

------------------------------------------------------------------------

# 12. Iterative DNS query

The slide deck explicitly covers **iterative resolution**.

## Definition

In iterative resolution, the contacted DNS server does NOT perform the
entire lookup for the requester.

Instead, it gives a **referral**:

> "I don't have the final answer. Ask this other server."

Then the local DNS resolver contacts the next server itself.

------------------------------------------------------------------------

## Example

Suppose:

``` text
Host = engineering.nyu.edu
```

wants an IP address for:

``` text
gaia.cs.umass.edu
```

The process can be:

``` text
Host
 |
 | 1
 v
Local DNS
 |
 | 2
 v
Root
 |
 | 3: referral to .edu
 v
.edu TLD
 |
 | 4: referral to umass authoritative
 v
Authoritative DNS
 |
 | 5: final answer
 v
Local DNS
 |
 | 6
 v
Host
```

### Key idea

Each server says:

``` text
"I don't know the final answer,
but I know who you should ask next."
```

------------------------------------------------------------------------

# 13. Recursive DNS query

Recursive resolution changes who carries the burden.

The client asks its local DNS resolver:

> "You find the answer for me."

The local DNS resolver takes responsibility for continuing the lookup.

Conceptually:

``` text
Host
 |
 | "Find IP for X"
 v
Local DNS
 |
 | asks Root
 v
Root
 |
 | asks TLD
 v
TLD
 |
 | asks Authoritative
 v
Authoritative
 |
 | answer
 v
Local DNS
 |
 | final answer
 v
Host
```

The client does not need to contact each hierarchy level itself.

------------------------------------------------------------------------

# 14. Iterative vs recursive --- MUST KNOW

  -----------------------------------------------------------------------
  Feature                 Iterative               Recursive
  ----------------------- ----------------------- -----------------------
  Who continues lookup?   Requesting              Contacted DNS server
                          resolver/client         

  Server gives referral?  Yes                     Normally no

  Server returns final    Not necessarily         Yes, if successful
  answer?                                         

  Example                 Local resolver asks     Host asks local DNS and
                          root, then TLD, then    local DNS does the work
                          authoritative           
  -----------------------------------------------------------------------

### Memory trick

**Iterative = "Here is who to ask next."**

**Recursive = "You ask everyone and come back with the answer."**

------------------------------------------------------------------------

# 15. Side-by-side lookup

## Iterative

``` text
Client → Local DNS
          |
          → Root
          ← "Ask TLD"
          |
          → TLD
          ← "Ask authoritative"
          |
          → Authoritative
          ← Answer
          |
          → Client
```

## Recursive

``` text
Client → Local DNS
          |
          | handles lookup
          ↓
        Root
          ↓
        TLD
          ↓
   Authoritative
          |
          ↓
      Final answer
          |
          ↓
        Client
```

### Exam trap

A DNS server can support recursive service while individual DNS
interactions in the hierarchy are iterative.

Do not assume:

``` text
DNS = always recursive
```

or:

``` text
DNS = always iterative
```

The mode depends on how the query is made and what the server is
configured to provide.

# 16. Why caching is essential

DNS lookup can involve several network messages.

Without caching:

``` text
Every client
    ↓
Local DNS
    ↓
Root
    ↓
TLD
    ↓
Authoritative
```

This creates unnecessary traffic and delay.

With caching:

``` text
First query:
Client → Local DNS → hierarchy → answer

Second query:
Client → Local DNS → cached answer
```

Much faster.

------------------------------------------------------------------------

# 17. DNS caching

A DNS resolver can store DNS information in its cache.

Example:

``` text
www.example.com → 93.184.216.34
```

After receiving this mapping, the resolver may cache it.

Later:

``` text
Another client asks the same question
              ↓
        Local DNS cache
              ↓
          immediate answer
```

The study notes specifically explain that cached information can allow
DNS servers to bypass root servers for most ordinary queries.

------------------------------------------------------------------------

# 18. TTL --- Time To Live

DNS records are cached only for a limited time.

This is controlled by the:

``` text
TTL
```

field.

TTL tells a resolver roughly:

> How long this record may remain cached before it should be
> discarded/revalidated.

Example:

``` text
www.example.com → 1.2.3.4
TTL = 3600 seconds
```

Means the cached record can be used for about:

``` text
3600 s = 1 hour
```

------------------------------------------------------------------------

## Why not cache forever?

Suppose a company changes:

``` text
Old IP = 1.2.3.4
New IP = 5.6.7.8
```

If every DNS server cached the old value forever, users could continue
reaching the wrong server.

TTL limits how long stale information can persist.

------------------------------------------------------------------------

# 19. What happens when an IP changes?

Suppose:

``` text
www.example.com
```

changes IP.

Some DNS resolvers may still have the old mapping cached.

They will continue using it until the cache entry expires.

After TTL expiry:

``` text
old cached record discarded
        ↓
new DNS lookup
        ↓
fresh authoritative information
```

### Important exam concept

DNS updates are not necessarily visible everywhere instantly.

Caching creates a temporary period during which different resolvers may
have different cached answers.

------------------------------------------------------------------------


The formal DNS RR wire format also includes fields such as:

``` text

TYPE

TTL
RDLENGTH
RDATA
```

# 21. Important DNS record types

## A record

Maps a hostname to an IPv4 address.

``` text
www.example.com
        ↓
A
        ↓
192.0.2.10
```

### Remember

``` text
A = IPv4 address
```

------------------------------------------------------------------------

## AAAA record

Maps a hostname to an IPv6 address.

``` text
AAAA → IPv6
```

### Memory

``` text
A  = IPv4
AAAA = IPv6
```

------------------------------------------------------------------------

## NS record

NS = **Name Server**

Specifies the authoritative name server for a domain/zone.

Example:

``` text
example.com
   ↓
NS
   ↓
ns1.example.com
```

### Memory

``` text
NS = "Who is the name server?"
```

------------------------------------------------------------------------

## CNAME record

CNAME = **Canonical Name**

Maps an alias to another hostname.

Example:

``` text
www.example.com
      ↓ CNAME
server.example.com
```

### Important

CNAME points to a **name**, not directly to an IP address.

------------------------------------------------------------------------

## MX record

MX = **Mail Exchange**

Specifies the mail server(s) responsible for receiving mail for a
domain.

Example:

``` text
example.com
      ↓
MX
      ↓
mail.example.com
```

MX records have a **preference** value.

Lower preference values are preferred.

Example:

``` text
10 mail1.example.com
20 mail2.example.com
```

`10` is preferred over `20`.

------------------------------------------------------------------------

## TXT record

Stores text associated with a domain.

Common uses include: - domain verification - email-related policies -
SPF-related information - other administrative/security data

------------------------------------------------------------------------

## SOA record

SOA = **Start of Authority**

Contains important administrative information about a DNS zone.

Think:

``` text
SOA = administrative information for the zone
```

The slide's extended record table highlights SOA as the record
associated with zone authority and defaults/contact information.

------------------------------------------------------------------------

# 22. DNS record cheat sheet

  Record   Meaning              Main use
  -------- -------------------- -------------------------------------
  A        IPv4 address         Hostname → IPv4
  AAAA     IPv6 address         Hostname → IPv6

  CNAME    Canonical Name       Alias → canonical hostname
  MX       Mail Exchange        Mail server for domain
  TXT      Text                 Verification/policy/text data

### Memorize

``` text
A     → IPv4
AAAA  → IPv6
NS    → Name Server
CNAME → Alias
MX    → Mail
TXT   → Text
SOA   → Zone authority
```

# 24. DNS header

The header contains a **16-bit Identification field**.

Purpose:

``` text
Query sent
   ↓
ID = 1234
   ↓
Reply comes back
   ↓
ID = 1234
   ↓
```

# 26. DNS message sections

## 26.1 Question section

Contains the query.

Important fields:

``` text
QNAME
QTYPE
QCLASS
```

Example:

``` text
QNAME  = www.example.com
QTYPE  = A
QCLASS = IN
```

Meaning:

> Give me the IPv4 address for www.example.com in the Internet class.

------------------------------------------------------------------------

## 26.2 Answer section

Contains records that answer the question.

Example:

``` text
www.example.com
A
93.184.216.34
```

------------------------------------------------------------------------

## 26.3 Authority section

Contains records pointing toward authoritative servers.

This is especially important in referrals.

------------------------------------------------------------------------

## 26.4 Additional section

Contains useful extra records related to the response.

For example, a response may provide the name of an authoritative server
and also include an A/AAAA record that gives that server's IP address.

### Memory

``` text
Answer     = actual answer
Authority  = who is authoritative
Additional = useful extra information
```

# 28. DNS Resource Record wire format

A resource record has:

``` text
NAME
TYPE
CLASS
TTL
RDLENGTH
RDATA
```

### What each means

**NAME** - Name to which the record belongs.

**TYPE** - Meaning of the record. - Examples: A, NS, CNAME, MX.

**CLASS** - Data class. - Internet class is `IN`.

**TTL** - Cache lifetime.

**RDLENGTH** - Length of the RDATA field.

**RDATA** - Actual data carried by the record.

# 30. DNSSEC --- why normal DNS is not enough

Normal DNS by itself does not authenticate that the answer really came
from the legitimate authority.

This creates security problems such as:

``` text
DNS cache poisoning
DNS response spoofing
```

Conceptually:

``` text
User asks:
www.bank.com → ?

Attacker tries:
"www.bank.com = attacker's IP"
```

If the false answer is accepted and cached, future users can be sent to
the wrong server.

------------------------------------------------------------------------

# 31. DNSSEC

DNSSEC = **Domain Name System Security Extensions**

The slide emphasizes:

-   DNSSEC provides **authentication**
-   DNSSEC provides **integrity**
-   DNSSEC uses digital signatures
-   trust is established through a chain

Conceptually:

``` text
Root
  ↓
TLD
  ↓
Authoritative zone
  ↓
DNS record
```

Each level participates in the chain of trust.

------------------------------------------------------------------------

## What DNSSEC does NOT provide

Very important:

DNSSEC does **not** provide confidentiality.

So:

``` text
DNSSEC
✓ Data-origin authentication
✓ Data integrity
✗ Confidentiality
```

This is explicitly supported by the DNSSEC specification.

------------------------------------------------------------------------

# 32. DNSSEC trust chain

The slide represents the trust relationship as:

``` text
Root
 ↓
TLD
 ↓
Authoritative
```

The idea is:

> The resolver can validate that the DNS data it receives is genuinely
> associated with the expected DNS hierarchy.

DNSSEC uses cryptographic signatures and public keys.

Important terms:

``` text
DNSKEY
DS
RRSIG
```

For exam-level understanding:

-   `DNSKEY` → public key material used for DNSSEC validation
-   `RRSIG` → digital signature over DNS resource-record sets
-   `DS` → delegation information linking a child zone into the chain of
    trust

------------------------------------------------------------------------

  ----------------------------------- -----------------------------------
  Name resolution                     Name resolution + cryptographic

  Does not inherently authenticate    Provides data-origin authentication

  -----------------------------------------------------------------------

### Memory

``` text
DNSSEC = "Can I trust this DNS data?"
Not = "Can anyone see this DNS query?"
```

# 34. DNS registration

How does a new domain become part of DNS?

Suppose an organization registers:

``` text
networkutopia.com
```

A domain registrar handles the registration process.

The authoritative DNS servers might be:

``` text
dns1.networkutopia.com
dns2.networkutopia.com
```

The DNS system needs delegation information so that resolvers can find
those authoritative servers.

------------------------------------------------------------------------

## Simplified registration process

``` text
Registrant
   ↓
Registrar
   ↓
TLD registry
   ↓
NS records for domain
   ↓
Authoritative DNS servers
   ↓
A/AAAA/MX/etc. records for hosts
```

The study notes describe the registrar ensuring that appropriate **NS**
and **A** records are entered into the TLD infrastructure.

------------------------------------------------------------------------

# 35. Domain registration --- important distinction

There are two different things:

### Registration/delegation

Tells the DNS hierarchy:

> "These servers are authoritative for this domain."

Usually involves:

``` text
NS records
```

### Zone data

The authoritative DNS server then stores records such as:

``` text
A
AAAA
CNAME
MX
TXT
SOA
```

So:

``` text
TLD delegation
      ↓
find authoritative DNS
      ↓
authoritative DNS
      ↓
actual host/mail records
```

# 41. DNS and application-layer protocols

DNS is itself an application-layer protocol, but other application-layer
protocols use it.

Example:

``` text
Browser
   |
   | needs IP for www.example.com
   v
DNS
   |
   | returns IP
   v
Browser
   |
   | HTTP/TCP connection
   v
Web server
```

Similarly:

``` text
SMTP
  ↓
DNS
  ↓
MX record
  ↓
Mail server
```

So DNS acts as infrastructure for other application-layer services.

# 42. Why DNS adds delay

Before the browser can contact the web server, it may first need DNS
resolution.

So:

``` text
DNS lookup
   +
TCP connection
   +
HTTP request/response
```

DNS therefore introduces additional delay.

But caching reduces this.

### Exam wording

> DNS adds an additional delay to applications that use it, but DNS
> caching can substantially reduce the lookup delay and query traffic.

# 43. DNS load distribution

Suppose:

``` text
www.example.com
```

has:

``` text
IP1
IP2
IP3
IP4
```

A DNS server can return all four addresses, potentially rotating their
order.

Example response 1:

``` text
IP1 IP2 IP3 IP4
```

Response 2:

``` text
IP3 IP4 IP1 IP2
```

Response 3:

``` text
IP2 IP1 IP4 IP3
```

If clients usually try the first address, this can distribute requests.

### Important

DNS rotation is a simple form of traffic distribution. It is not the
same thing as a full load balancer.

# 44. DNS cache poisoning

## Attack idea

Suppose the correct mapping is:

``` text
bank.example → 10.0.0.1
```

Attacker tries to inject:

``` text
bank.example → 10.0.0.99
```

If a resolver accepts and caches the false response:

``` text
Future clients
     ↓
Local DNS cache
     ↓
10.0.0.99
```

This is DNS cache poisoning.

------------------------------------------------------------------------

# 45. Why DNSSEC helps

DNSSEC adds cryptographic signatures.

The resolver can validate:

``` text
"Did this DNS data actually come from the
expected signed DNS hierarchy?"
```

If validation fails, forged data can be rejected.

### Remember

``` text
DNSSEC protects authenticity + integrity.

It does NOT encrypt DNS data.
```

# 48. Very important comparison: caching vs authoritative data

## Cached data

-   temporary
-   controlled by TTL
-   may become stale
-   useful for reducing DNS traffic and delay

## Authoritative data

-   comes from the authoritative source for the zone
-   represents the zone's current DNS data as served by that authority

### Exam trap

A cached answer is not automatically authoritative just because it is
correct.

# 49. Common exam traps

## Trap 1

**"There are 13 DNS root servers."**

Better answer:

> There are 13 logical root server identities, with many replicated
> instances distributed worldwide.

------------------------------------------------------------------------

## Trap 2

**"TLD server stores the IP address of every host."**

Wrong.

TLD servers mainly help direct queries to authoritative DNS servers.

------------------------------------------------------------------------

## Trap 3

**"Authoritative server always means root server."**

Wrong.

An authoritative server is authoritative for a particular zone.

------------------------------------------------------------------------

## Trap 4

**"Local DNS is one of the hierarchy levels."**

Not in the same sense as root/TLD/authoritative.

The local resolver is a client-facing resolver/cache/proxy.

------------------------------------------------------------------------

## Trap 5

**"Recursive query means the client asks every server recursively."**

Wrong.

Recursive means the contacted server takes responsibility for obtaining
the answer.

------------------------------------------------------------------------

## Trap 6

**"Iterative query means the server returns the final answer."**

Not necessarily.

It can return a referral to another server.

------------------------------------------------------------------------

## Trap 7

**"DNSSEC encrypts DNS."**

Wrong.

DNSSEC provides authentication/integrity, not confidentiality.

------------------------------------------------------------------------

## Trap 8

**"CNAME contains an IP address."**

Normally:

``` text
CNAME → another hostname
```

------------------------------------------------------------------------

## Trap 9

**"MX gives an IP address directly."**

MX identifies the mail server hostname and has preference information.
That mail server name can then be resolved using A/AAAA records.

------------------------------------------------------------------------

## Trap 10

**"TTL means the DNS server must delete the authoritative record after
TTL."**

Wrong.

TTL mainly controls how long a cached resource record may be used before
it should be discarded/revalidated.

------------------------------------------------------------------------

# 51. Case: company changes its IP address

Question:

> A company changes its web server IP. Why do some users still reach the
> old IP?

Answer:

1.  DNS resolvers may have cached the old record.
2.  The cached record has a TTL.
3.  Until the TTL expires, the resolver may continue using the cached
    mapping.
4.  After expiration, a fresh lookup can obtain the new record.

------------------------------------------------------------------------

# 52. Case: DNS query is slow

Possible causes:

-   local cache miss
-   multiple DNS hierarchy lookups
-   network delay
-   distant DNS server
-   DNS server load
-   slow response from authoritative server

Caching usually reduces repeated lookup cost.

------------------------------------------------------------------------

# 53. Case: root server is not contacted

Possible reason:

``` text
The local/recursive DNS resolver already cached:
- the final answer, or
- enough delegation information
```

Therefore it may bypass the root.

------------------------------------------------------------------------

# 54. Case: user receives multiple IP addresses

Likely explanation:

``` text
The hostname is associated with multiple servers.
```

DNS can return multiple IP addresses.

The order may be rotated to help distribute traffic.

------------------------------------------------------------------------

# 55. Case: DNS response says "ask another server"

This is a **referral**.

It is characteristic of **iterative resolution**.

Example:

``` text
Root:
"I don't have the final IP.
Ask these .com TLD servers."
```

# 59. The complete DNS story in 60 seconds

Memorize this paragraph:

> DNS is a distributed hierarchical application-layer naming system that
> maps hostnames to IP addresses and also supports services such as host
> aliasing, mail-server aliasing, and load distribution. A client
> normally contacts a local DNS resolver, which may answer from its
> cache. If the answer is not cached, the resolver can query the DNS
> hierarchy involving root, TLD, and authoritative servers. In iterative
> resolution, servers return referrals and the resolver continues the
> lookup; in recursive resolution, the contacted resolver performs the
> lookup on behalf of the requester. DNS records contain mappings such
> as A, AAAA, NS, CNAME, MX, TXT, and SOA. DNS messages contain a
> header, question, answer, authority, and additional sections. DNS
> caching reduces delay and traffic, with TTL controlling cache
> lifetime. DNSSEC adds data-origin authentication and integrity through
> cryptographic signatures but does not provide confidentiality.

# 61. Exam questions from the slide deck --- what you should be able to answer

### 1. Why can't we simply use IP addresses everywhere?

Because humans prefer stable, meaningful names, while IP addresses can
change. DNS provides a naming abstraction over IP addressing.

### 2. Why isn't DNS centralized?

Single point of failure, enormous traffic, maintenance difficulty, and
geographic distance.

### 3. What is the difference between a domain and a zone?

A domain is a namespace/subtree; a zone is an administratively managed
portion of that namespace.

### 4. What does the root server do?

It directs the resolver toward the appropriate TLD servers.

### 5. What does a TLD server do?

It directs the resolver toward authoritative DNS servers for the
requested domain.

### 6. What does an authoritative DNS server do?

It serves authoritative records for its zone.

### 7. What does the local DNS server do?

It serves clients, caches DNS information, and can perform/forward DNS
resolution.

### 8. Difference between iterative and recursive DNS?

Iterative returns referrals; recursive causes the contacted
resolver/server to pursue the lookup and return the result.

### 9. Why is caching useful?

It reduces DNS lookup delay and DNS traffic.

### 10. What does TTL do?

Controls how long a cached resource record can be used.

### 11. What is an A record?

Hostname → IPv4 address.

### 12. What is an AAAA record?

Hostname → IPv6 address.

### 13. What is an NS record?

Identifies a name server authoritative for a domain/zone.

### 14. What is a CNAME?

Maps an alias to a canonical hostname.

### 15. What is an MX record?

Identifies mail exchange server(s) for a domain.

### 16. What is DNSSEC?

A set of DNS security extensions providing data-origin authentication
and integrity.

### 17. Does DNSSEC provide confidentiality?

No.

### 18. What is the DNS message structure?

Header + Question + Answer + Authority + Additional.

### 19. What is the DNS transaction ID?

A 16-bit identifier used to associate a response with its query.

### 20. What does AA mean?

Authoritative Answer.

### 21. What does RD mean?

Recursion Desired.

### 22. What does RA mean?

Recursion Available.

### 23. What does `dig +trace` do?

It follows the DNS delegation hierarchy to show the resolution path.
