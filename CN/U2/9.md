# 1. Where Selective Repeat Fits

The slide deck places this topic under:

```text
Transport Layer
→ Principles of reliable data transfer
```

The reliable-data-transfer progression is:

```text
Stop-and-Wait
      ↓
Pipelined RDT
      ↓
Go-Back-N (GBN)
      ↓
Selective Repeat (SR)
```

The purpose of SR is to improve the retransmission behavior of GBN.

---

# 2. Why Do We Need Selective Repeat?

GBN allows pipelining, but it can retransmit packets unnecessarily.

Example:

```text
Packets sent:
0 1 2 3 4 5

Packet 2 is lost.

Packets 3, 4, 5 arrive correctly.
```

Basic GBN receiver:

```text
discard 3
discard 4
discard 5
```

When timeout occurs, the sender may retransmit:

```text
2 3 4 5
```

Packets 3, 4, and 5 were already received correctly.

That wastes:

```text
bandwidth
transmission time
receiver processing
```

Selective Repeat solves this by retransmitting only the packets that actually need retransmission.

---

# 3. Definition of Selective Repeat

**Selective Repeat (SR)** is a pipelined reliable-data-transfer protocol in which:

- multiple packets can be in flight
- the sender maintains a window of size `N`
- packets are individually acknowledged
- correctly received out-of-order packets can be buffered
- only the required/lost packets are retransmitted

Core idea:

```text
GBN:
retransmit from loss onward

SR:
retransmit selectively
```

---

# 4. Why Is It Called "Selective Repeat"?

Because the sender selectively repeats packets that require retransmission.

Suppose:

```text
0 1 2 3 4
```

and only packet 2 is lost.

SR does:

```text
retransmit 2
```

rather than:

```text
retransmit 2 3 4
```

provided 3 and 4 were correctly received and acknowledged.

---

# 5. Main Difference Between GBN and SR

| Feature | Go-Back-N | Selective Repeat |
|---|---|---|
| ACK | Cumulative | Individual/selective |
| Out-of-order packet | Basic GBN discards | SR buffers |
| Retransmission | Missing packet onward | Only required packet |
| Receiver buffering | Lower | Higher |
| Receiver complexity | Lower | Higher |
| Unnecessary retransmissions | More | Fewer |

Memory:

```text
GBN = go back and resend many

SR = select the packet and repeat only it
```

---

# 6. Pipelining

The slide on **page 3** begins with:

```text
pipelining: multiple packets in flight
```

Pipelining means the sender does not wait for an ACK after every single packet.

Instead:

```text
send pkt0
send pkt1
send pkt2
send pkt3
...
```

can occur before all acknowledgments return.

This improves channel utilization compared with stop-and-wait.

---

# 7. Why Pipelining Needs a Window

Without a window, the sender could theoretically place an unlimited number of packets into the network.

SR limits the number of outstanding packets to:

```text
N
```

where:

```text
N = window size
```

Therefore:

```text
maximum outstanding unacknowledged packets = N
```

The window also determines which sequence numbers are currently usable.

---

# 9. `send_base`

Definition:

```text
send_base =
sequence number of the oldest
unacknowledged packet
```

It is the left edge of the sender's window.

Example:

```text
Packets:
0 1 2 3 4 5

ACKed:
0 1

Outstanding:
2 3 4

send_base = 2
```

---

# 10. `nextseqnum`

Definition:

```text
nextseqnum =
sequence number of the next packet
that has not yet been sent
```

Example:

```text
Sent:
0 1 2 3

nextseqnum = 4
```

# 11. Sender Sequence-Number Regions

The SR sender diagram on page 4 distinguishes several regions.

Conceptually:

```text
Already ACKed
      |
      ↓
[ ... ]
        [ SENT, NOT ACKED ]
                  |
                  ↓
             [ WINDOW ]
                  |
                  ↓
        [ USABLE, NOT YET SENT ]
                  |
                  ↓
              NOT USABLE
```

The exact window boundaries move as ACKs arrive.

---

# 12. Sender Window Size

If:

```text
N = 4
```

then the sender can have up to:

```text
4 packets
```

in the pipeline/window.

Example:

```text
[0 1 2 3]
```

If ACKs arrive for some packets, the window advances and new packets become eligible for transmission.

---

# 13. SR Receiver Window

Unlike basic GBN, the SR receiver also maintains a window.

Important variable:

```text
rcv_base
```

Definition:

```text
rcv_base =
sequence number of the lowest
packet not yet delivered in order
```

It represents the left edge/base of the receiver's current window.

---

# 14. Receiver Window

The slide on page 4 shows the receiver's sequence-number space.

There are three important conceptual regions:

```text
already received / buffered
expected and acceptable
outside the receiver window
```

An out-of-order packet can be acceptable if it lies within the receiver's window.

This is a major difference from basic GBN.

---

# 15. Individual ACKs

SR uses:

> **Individual acknowledgments**

If packet 3 is correctly received:

```text
ACK3
```

means packet 3 itself was correctly received.

Unlike GBN, an ACK for packet 3 does not automatically mean that every earlier packet has been received.

This is why SR can selectively retransmit.

---

# 16. Why Individual ACKs Are Necessary

Suppose:

```text
Packets:
0 1 2 3
```

Packet 2 is lost.

Packets 3 and 4 may still arrive.

If the receiver individually acknowledges:

```text
ACK3
ACK4
```

the sender knows:

```text
3 received correctly
4 received correctly
```

and therefore does not need to retransmit them.

Only packet 2 needs retransmission.

---

# 17. SR Sender — Data From Above

The sender receives data from the upper layer.

If the next available sequence number lies inside the sender window:

```text
packetize
↓
assign sequence number
↓
send
```

If the sequence number is outside the current sender window:

```text
cannot send immediately
```

The data may need to be buffered or returned to the upper layer until the window advances.

---

# 18. SR Sender — ACK Received

When an ACK arrives:

```text
mark that packet as ACKed
```

This is different from GBN.

GBN mainly advances its base based on cumulative ACK progress.

SR can have a situation like:

```text
ACK0
ACK2
```

while packet 1 is still unacknowledged.

The sender therefore remembers which individual packets in the window have been acknowledged.

---

# 19. Example of Selective ACK State

Suppose:

```text
Sender window:
[0 1 2 3]
```

ACKs received:

```text
ACK0
ACK2
```

Then:

```text
0 = ACKed
1 = NOT ACKed
2 = ACKed
3 = not yet ACKed
```

The sender does not retransmit 0 or 2.

If packet 1 times out:

```text
retransmit packet 1 only
```

---

# 20. SR Sender — When Does the Window Move?

The sender window moves when:

```text
the packet at send_base becomes ACKed
```

Then:

```text
send_base
```

moves forward to the smallest sequence number that is still unacknowledged.

Example:

```text
Before:

send_base = 2

2 = ACKed
3 = ACKed
4 = not ACKed
5 = not ACKed
```

Then:

```text
send_base moves to 4
```

The window advances over the consecutively ACKed packets.

---

# 21. Window Movement Example

Suppose:

```text
sender window:
[2 3 4 5]
```

ACKs:

```text
ACK3
```

arrives first.

Packet 2 is still unacknowledged.

Therefore:

```text
send_base stays at 2
```

Even though packet 3 has been individually acknowledged.

Later:

```text
ACK2
```

arrives.

Now:

```text
2 and 3 are ACKed
```

So:

```text
send_base moves to 4
```

This is a very important SR concept.

---

# 22. SR Sender Timeout

The slide on page 5 shows the sender maintaining:

```text
timer
```

SR uses timers to detect lost packets.

Crucial difference from GBN:

```text
GBN:
one timer conceptually associated with oldest outstanding packet

SR:
each outstanding packet needs its own logical timer
```

The textbook notes that one hardware timer can be used to implement multiple logical timers, but conceptually SR needs a timer per outstanding packet because timeout causes only that packet to be retransmitted.

---

# 23. What Happens When an SR Timer Expires?

Suppose:

```text
Packets:
0 1 2 3

ACK0
ACK1
ACK3
```

Packet 2 remains unacknowledged.

If packet 2's timer expires:

```text
retransmit packet 2 only
```

Not:

```text
2 3
```

because packet 3 has already been acknowledged.

This is the key benefit of SR.

---

# 24. SR Receiver — Correct Packet Inside Window

The study material describes the receiver behavior precisely.

If a packet with sequence number:

```text
n ∈ [rcv_base, rcv_base + N - 1]
```

is correctly received:

```text
send selective ACK(n)
```

Then:

```text
if packet was not previously received:
    buffer it
```

If:

```text
n == rcv_base
```

then the packet can be delivered to the upper layer.

---

# 25. Out-of-Order Packet in SR

Suppose:

```text
rcv_base = 2
```

and packet:

```text
3
```

arrives correctly.

Packet 3 is:

```text
out of order
```

But unlike GBN:

```text
SR does NOT discard it.
```

Instead:

```text
buffer packet 3
send ACK3
```

This is one of the highest-priority MCQ differences.

---

# 26. Why Buffer Out-of-Order Packets?

Suppose:

```text
Expected:
2

Received:
3
4
5
```

SR can:

```text
buffer 3
buffer 4
buffer 5
ACK3
ACK4
ACK5
```

When packet 2 finally arrives:

```text
deliver 2
deliver buffered 3
deliver buffered 4
deliver buffered 5
```

This avoids retransmitting packets that were already correctly received.

---

# 27. Study-Note Example — Packet 2 Lost

Suppose:

```text
2 is lost
3, 4, 5 arrive
```

SR receiver:

```text
buffer 3
buffer 4
buffer 5
```

and sends:

```text
ACK3
ACK4
ACK5
```

When packet 2 finally arrives:

```text
deliver 2
then deliver 3, 4, 5
```

The Kurose/Ross material specifically describes the receiver initially buffering packets 3, 4, and 5 and delivering them together with packet 2 once packet 2 arrives.

---

# 28. SR Receiver — Packet Below Window

The study material describes another important receiver case.

If a correctly received packet lies in:

```text
[rcv_base - N, rcv_base - 1]
```

then it is a packet that the receiver has previously acknowledged.

The receiver should:

```text
send an ACK again
```

rather than simply ignoring it.

Why?

Because its earlier ACK may have been lost.

This allows the sender to learn that the packet was successfully received.

---

# 29. SR Receiver — Packet Outside Relevant Ranges

If the packet is neither:

```text
inside the current receiver window
```

nor:

```text
in the previously acknowledged region
```

then the receiver can:

```text
ignore it
```

So the conceptual receiver cases are:

```text
1. Current acceptable window
   → ACK + buffer/deliver

2. Previously ACKed region
   → re-ACK

3. Otherwise
   → ignore
```

---

# 30. SR Receiver — When Does the Window Move?

The receiver window moves when:

```text
rcv_base packet
```

has been correctly received.

If there are already buffered consecutive packets immediately after it, those can also be delivered.

Example:

```text
rcv_base = 2

buffer:
3 4 5

packet 2 arrives
```

Then:

```text
deliver 2
deliver 3
deliver 4
deliver 5
```

The receiver window moves forward by the number of newly deliverable consecutive packets.

---

# 31. Page 5 — SR Sender and Receiver Rules

The slide contains sender and receiver pseudocode-style rules.

### Sender

When data arrives from above:

```text
if next sequence number is inside window:
    send packet
```

On timeout:

```text
resend packet
restart timer
```

On ACK(n):

```text
mark packet n as received
if n is the smallest unACKed packet:
    advance window base to next unACKed packet
```

---

### Receiver

If:

```text
packet n ∈ [rcvbase, rcvbase + N - 1]
```

then:

```text
send ACK(n)
```

and:

```text
buffer packet n
```

If packet n is the current base:

```text
deliver packet
advance window
deliver any consecutive buffered packets
```

Otherwise:

```text
ignore
```


The sender knows:

```text
ACK2
```

```text
send_base moves from 2 to 4
```

The slide explicitly asks this.

The window advances by four positions in the illustrated example.

```text
Packet 2 was the missing base packet.
ACK2 arrives.
↓

↓

↓

↓
new packets become available to send.
```


```text
pkt6
pkt7
pkt8
pkt9
```

for the illustrated window state.

# 37. Why Does the Window Jump?

This is easy to misunderstand.

SR ACKs packets individually.

However, the sender's window base is always:

```text
smallest unacknowledged packet
```

So if several consecutive packets have already been ACKed, receiving the ACK for the current base can cause the window to jump over all those already-ACKed packets.

Example:

```text
Before:

2 = unACKed
3 = ACKed
4 = ACKed
5 = ACKed

ACK2 arrives

After:

2 = ACKed
3 = ACKed
4 = ACKed
5 = ACKed

base → 6
```


For the slide's particular state:


Only packets that are missing/unacknowledged.

Therefore after the first round:

```text
packet 5 → missing
packet 10 → missing
```

Packets:

```text
1 2 3 4 6 7 8 9
```

do not need retransmission.

```text
5 10
```

```text
not lost
```

All 10 original packets have now been received.

# 45. Why SR Needs More Receiver Memory

GBN can simply do:

```text
out-of-order
→ discard
```

SR instead does:

```text
out-of-order
→ buffer
→ individually ACK
```

Therefore SR needs more receiver memory and state.

Trade-off:

```text
more complexity
        ↓
fewer unnecessary retransmissions
```

Suppose:

```text
Packets:
0 1 2 3

ACK0
ACK1
ACK3

packet2 missing
```

Only packet 2 needs retransmission.

Therefore its timeout must be independently detectable.

Conceptually:

```text
timer0
```

for outstanding packets.

# 47. SR Sender Window — Key State

A useful conceptual representation is:

```text
send_base
    |
    ↓
[ 2 3 4 5 ]
    ↑
 nextseqnum
```

Inside the window, individual packets may have different states:

```text
ACKed
sent but not ACKed
not yet sent
```

Unlike GBN, the window can contain a mixture of:

```text
ACKed + unACKed
```

packets.

# 48. SR Receiver Window — Key State

The receiver maintains:

```text
rcv_base
```

and a window of acceptable sequence numbers:

```text
[rcv_base ... rcv_base + N - 1]
```

Within this range:

```text
correct packet
→ ACK
→ buffer if needed
```

When the base packet arrives:

```text
deliver it
+
deliver consecutive buffered packets
+
advance receiver window
```

# 49. Sequence Numbers in SR

If the sequence-number field has:

```text
k bits
```

the sequence-number space contains:

```text
2^k
```

values:

```text
0 ... 2^k - 1
```

Arithmetic wraps around modulo:

```text
2^k
```

Example with 3 bits:

```text
0 1 2 3 4 5 6 7 0 1 2 ...
```

# 50. The SR Sequence-Number Dilemma

This is one of the most technical and important parts of the slide deck.

The problem occurs because sequence numbers are finite and eventually wrap around.

The receiver must distinguish:

```text
old retransmitted packet
```

from:

```text
new packet with the same sequence number
```

If the window is too large, the receiver may not be able to tell them apart.

# 52. First Scenario — ACKs Arrive

Suppose:

```text
packets 0, 1, 2
```

are sent and correctly received.

Receiver then advances its window.

With sequence numbers:

```text
0 1 2 3
```

the sequence numbers wrap around.

New packets can again use:

```text
0
1
...
```

---

# 53. Second Scenario — ACKs Are Lost

Now suppose:

```text
packets 0 1 2
```

were successfully received, but their ACKs are lost.

The sender times out and retransmits.

The sender may retransmit:

```text
packet 0
```

The receiver has already advanced its window and may now consider sequence number 0 acceptable as a new packet.

But is it:

```text
old packet 0 being retransmitted?
```

or:

```text
new packet 0?
```

The receiver cannot tell from the sequence number alone.

---

# 54. The SR Ambiguity

This is the central problem.

The receiver sees:

```text
sequence number = 0
```

But it cannot determine whether it represents:

```text
old packet 0
```

or:

```text
new packet 0
```

If it accepts an old retransmission as new data:

```text
duplicate data
```

can be delivered to the application.

That breaks reliable data transfer.

---

# 55. Page 10 — "No Problem" vs "Oops"

The slide presents two scenarios.

### Scenario (a)

The receiver window after receipt is positioned so that the retransmitted packet is not accepted as a new packet.

This is:

```text
no problem
```

---

### Scenario (b)

The receiver window is positioned so that the same sequence number falls inside its acceptable window.

The receiver may interpret the old packet as new.

This is:

```text
oops
```

The problem is caused by an insufficiently large sequence-number space relative to the window size.

---

# 56. Why Window Size Must Be Limited

The Kurose/Ross material explains that the sequence-number space must be large enough to distinguish old retransmissions from new packets.

For SR:

```text
window size ≤ half of sequence-number space
```

If:

```text
sequence-number space = S
```

then:

```text
N ≤ S/2
```

Equivalently:

```text
2N ≤ S
```

---

# 57. With k-Bit Sequence Numbers

If:

```text
k = number of sequence-number bits
```

then:

```text
S = 2^k
```

For SR:

```text
N ≤ 2^(k-1)
```

Equivalently:

```text
2N ≤ 2^k
```

This is a high-value numerical/MCQ formula.

---

# 58. Example of the SR Window Rule

Suppose:

```text
k = 3
```

Then:

```text
sequence-number space = 2^3 = 8
```

Therefore maximum SR window:

```text
N ≤ 8/2
N ≤ 4
```

So:

```text
Nmax = 4
```

# 59. Another Example

Suppose:

```text

```

Then:

```text

```

Maximum safe SR window:

```text
8
```

Since:

```text
S = 2^k
```

the condition becomes:

```text
2^k ≥ 2N
```

or:

```text
N ≤ 2^(k-1)
```

Memorize this.

# 63. Why Half?

The sequence-number space needs enough room for:

```text
current/acceptable packets
```

and also enough separation from:

```text
old packets that may still be delayed/retransmitted
```

If the windows overlap too much after sequence-number wraparound, an old packet can look identical to a new packet.

The half-space rule provides the necessary separation.

# 64. Important SR Receiver Cases

Memorize these three.

### Case 1 — Packet inside current window

```text
correct packet
→ ACK it
→ buffer if not already received
→ if it is base, deliver consecutive packets
```

### Case 2 — Packet below current window but recently ACKed

```text
re-ACK it
```

because its previous ACK may have been lost.

### Case 3 — Packet outside relevant range

```text
ignore
```

---

# 65. Important SR Sender Cases

### Case 1 — Data from upper layer

If sequence number is inside sender window:

```text
send packet
```

Otherwise:

```text
buffer/wait
```

### Case 2 — Timeout

```text
retransmit that packet
restart its timer
```

### Case 3 — ACK(n)

```text
mark packet n as ACKed
```

If:

```text
n == send_base
```

then:

```text
advance send_base
```

past all consecutive ACKed packets.

---

# 66. SR Complete Example

Suppose:

```text
window = 4

send:
0 1 2 3
```

Packet 1 is lost.

Receiver receives:

```text
0
2
3
```

SR:

```text
0 → deliver + ACK0
2 → buffer + ACK2
3 → buffer + ACK3
```

Sender state:

```text
0 = ACKed
1 = unACKed
2 = ACKed
3 = ACKed
```

Therefore:

```text
send_base = 1
```

Packet 1's timer expires:

```text
retransmit packet 1
```

Receiver gets packet 1:

```text
deliver 1
```

Since 2 and 3 are already buffered:

```text
deliver 2
deliver 3
```

Then receiver window moves forward.

---

# 67. Why SR Is More Efficient Than GBN

Suppose:

```text
100 packets
1 packet lost
99 packets received correctly
```

GBN can potentially retransmit:

```text
lost packet
+
many later packets
```

SR retransmits:

```text
only the lost packet
```

As the window and bandwidth-delay product become large, this difference can become significant.

---

# 68. Why SR Is More Complex

SR requires:

```text
individual ACK state
individual packet timers
receiver buffering
sequence-number/window management
```

Therefore:

```text
SR efficiency ↑
SR complexity ↑
```

# 69. SR vs GBN — Exam Table

| Concept | GBN | SR |
|---|---|---|
| Pipelining | Yes | Yes |
| Window | N | N |
| ACK | Cumulative | Individual |
| Out-of-order packet | Discard in basic protocol | Buffer |
| Out-of-order ACK | Duplicate cumulative ACK | Individual ACK |
| Retransmission | From oldest missing onward | Only timed-out/lost packet |
| Timer | Oldest outstanding | Per outstanding packet conceptually |
| Receiver buffering | Low | Higher |
| Receiver complexity | Lower | Higher |
| Retransmission waste | Higher | Lower |
| Sequence-number/window constraint | Less restrictive | `N ≤ S/2` |
| Main idea | Go back | Select and repeat |

# 70. SR vs Stop-and-Wait

| Feature | Stop-and-Wait | SR |
|---|---|---|
| Packets in flight | 1 | Up to N |
| Pipelining | No | Yes |
| ACKs | Individual | Individual |
| Out-of-order buffering | Not needed | Required |
| Retransmission | One packet | Selective |
| Window | 1 | N |
| Utilization | Lower | Higher |

# 71. Numerical Problem — General SR Method

For a problem like the slide's:

```text
Every kth transmission is lost
M original packets
window = N
```

Do this:

### Step 1

Transmit the initial window.

### Step 2

Count actual transmissions globally.

### Step 3

Mark every kth transmission as lost.

### Step 4

At the receiver:

```text
correct + in-order → deliver + ACK
correct + out-of-order → buffer + individual ACK
```

### Step 5

Only missing/unacknowledged packets need retransmission.

### Step 6

Continue counting transmissions globally.

### Step 7

Stop when every original packet has been received and acknowledged.

# 72. SR Numerical Problem — Common Mistake

Do NOT treat SR like GBN.

Wrong:

```text
packet 5 lost
→ retransmit 5 6 7 8 9
```

Correct:

```text
packet 5 lost
→ retransmit 5 only
```

provided:

```text
6 7 8 9
```

were correctly received and acknowledged.

# 74. High-Yield MCQ Traps

## Trap 1

SR uses cumulative ACKs.

**False.**

SR uses individual/selective ACKs.

---

## Trap 2

SR discards out-of-order packets.

**False.**

SR can buffer correctly received out-of-order packets.

---

## Trap 3

SR retransmits all packets after a lost packet.

**False.**

It retransmits only packets requiring retransmission.

---

## Trap 4

`send_base` is the next packet to send.

**False.**

It is the smallest sequence number of the unacknowledged sender packet.

---

## Trap 5

`nextseqnum` is the oldest unacknowledged packet.

**False.**

It is the next sequence number available for a new packet.

---

## Trap 6

ACK3 necessarily means packets 0, 1, 2, and 3 are all ACKed.

**False for SR.**

ACK3 individually acknowledges packet 3.

---

## Trap 7

If ACK3 arrives before ACK2, SR must immediately move `send_base` to 4.

**False.**

`send_base` remains at 2 until packet 2 is acknowledged.

---

## Trap 8

When ACK2 arrives after ACK3, the base can jump past both.

**True.**

If 3 was already ACKed, both can now be passed.

---

## Trap 9

SR requires no receiver buffering.

**False.**

Buffering is a fundamental part of SR's handling of out-of-order packets.

---

## Trap 10

SR can use any window size regardless of sequence-number space.

**False.**

The standard SR rule requires:

```text
N ≤ S/2
```

---

## Trap 11

With k-bit sequence numbers, SR window can be as large as `2^k - 1`.

**False.**

Maximum safe window:

```text
2^(k-1)
```

under the standard SR constraint.

---

## Trap 12

For the slide's numerical example, the SR answer is 18.

**False.**

```text
18 = GBN example
12 = SR example
```

# 75. Important Formulas

### Sequence-number space

```text
S = 2^k
```

where `k` is the number of sequence-number bits.

### SR window constraint

```text
N ≤ S/2
```

Therefore:

```text
N ≤ 2^(k-1)
```

Equivalent:

```text
2N ≤ S
```

or:

```text
2N ≤ 2^k
```

---

# 76. Worked Sequence-Number Example

Suppose:

```text
k = 4 bits
```

Then:

```text
S = 2^4 = 16
```

Maximum SR window:

```text
N ≤ 16/2
N ≤ 8
```

Therefore:

```text
Nmax = 8
```

A window of 9 would violate the standard SR constraint.

---

# 77. Worked Sequence-Number Example 2

Suppose:

```text
N = 5
```

Then SR requires:

```text
S ≥ 2N
S ≥ 10
```

The sequence-number space must contain at least 10 values.

Since sequence spaces are powers of two for a k-bit field:

```text
2^3 = 8   → insufficient
2^4 = 16  → sufficient
```

Therefore at least:

```text
k = 4 bits
```

are required.

# 78. Deep Concept — Why ACKing Below the Window Matters

Suppose:

```text
packet n
```

was received and ACKed.

But:

```text
ACK(n)
```

was lost.

The sender may retransmit packet n.

By then the receiver window may have advanced.

If the receiver simply ignored packet n, the sender might never learn that the packet had already been successfully received.

Therefore SR can:

```text
re-ACK an old but previously acknowledged packet
```

when it falls into the relevant previous window region.

This is why the receiver behavior is more complicated than simply:

```text
accept or reject
```

---

# 79. Deep Concept — Why Sequence Numbers Need Separation

Finite sequence numbers wrap:

```text
0 1 2 3
↓
0 1 2 3
```

Therefore:

```text
old packet 0
```

and:

```text
new packet 0
```

can have the same identifier.

The receiver therefore needs the window size to be small enough that an old packet cannot fall into the current acceptable window and be mistaken for a new packet.

Hence:

```text
N ≤ S/2
```

# 84. Final Rules to Memorize

```text
1. SR is a pipelined reliable-data-transfer protocol.

2. SR uses a sender window and receiver window.

3. Window size = N.

4. send_base = smallest sequence number of an
   unacknowledged sender packet.

5. nextseqnum = next unused sequence number.

6. rcv_base = base of receiver's current window.

7. SR uses individual/selective ACKs.

8. Correct out-of-order packets can be buffered.

9. Buffered packets can be delivered once the missing
   lower sequence numbers arrive.

10. A timeout retransmits only the corresponding packet.

11. ACKing a packet other than send_base does not necessarily
    move send_base.

12. When send_base becomes ACKed, the base advances over all
    consecutively ACKed packets.

13. SR may re-ACK packets from the previous window because
    their original ACK may have been lost.

14. Finite sequence numbers wrap around.

15. SR needs enough sequence-number space to distinguish
    old retransmissions from new packets.

16. Standard SR constraint:
    N ≤ S/2.

17. If k sequence-number bits are used:
    S = 2^k
    N ≤ 2^(k-1).

18. In the uploaded SR numerical example:
    10 original transmissions + 2 retransmissions = 12.

19. The corresponding GBN example gives 18 because GBN
    retransmits correctly received out-of-order packets.

20. The single most important conceptual distinction:
    GBN throws away out-of-order data;
    SR keeps it.
```
