# 2. UDP — User Datagram Protocol

UDP is a **connectionless transport-layer protocol**.

The slide on **page 4** describes UDP as a:

> **“no frills,” “bare bones” Internet transport protocol**

It provides a **best-effort service**.

That means UDP does not guarantee that every segment:

- arrives
- arrives in order
- arrives without corruption

UDP leaves many reliability functions to the application if they are required.

---

# 3. What Does “Connectionless” Mean?

UDP is connectionless because:

> No handshaking occurs between the UDP sender and receiver before a UDP segment is transmitted.

Flow:

```text
Application
    ↓
UDP
    ↓
Send segment
```

There is no TCP-style:

```text
SYN
SYN-ACK
ACK
```

connection establishment.

Each UDP segment is handled independently.

---

# 4. UDP Characteristics

From the slide deck and study notes, UDP has these important properties:

- connectionless
- no connection establishment
- simple
- low overhead
- best-effort
- no reliability guarantee
- no ordering guarantee
- no built-in retransmission
- no built-in flow control
- no TCP-style congestion control
- each UDP segment can be handled independently
- application can implement additional reliability if needed

---

# 5. UDP Does NOT Guarantee

UDP does not guarantee:

```text
Delivery
Ordering
Retransmission
Duplicate elimination
Flow control
Congestion control
```

For example:

```text
Sender:

A → B → C

Possible receiver outcome:

A → C
```

`B` may be lost.

Or:

```text
A → C → B
```

could occur because UDP itself does not provide in-order delivery.

# 6. Why Is UDP Used?

The slide on **page 4** gives the reasons for UDP's simplicity.

### 1. No connection establishment

No handshake delay.

This can reduce startup latency.

---

### 2. Simple

UDP has relatively little transport-layer state and processing.

---

### 3. Small header size

UDP has only:

```text
8 bytes
```

of transport-layer header overhead.

This is much smaller than TCP's minimum header.

---

### 4. No congestion control

UDP does not automatically throttle the sender according to network congestion in the way TCP does.

This can be useful for applications that need to control their own sending behavior.

However:

> UDP applications sending aggressively can contribute to network congestion.

---

### 5. Application-controlled behavior

An application can add its own:

- reliability
- retransmission
- ordering
- timing
- rate control

when needed.

# 7. Why Would Anyone Use UDP?

The slide asks:

> Why is there UDP?

The study notes give the important reasoning.

UDP can be useful when the application:

- can tolerate some loss
- needs low overhead
- does not want connection-establishment delay
- wants to implement its own reliability/control
- benefits from simple datagram semantics

The exact tradeoff depends on the application.

# 10. UDP vs TCP — Why UDP Can Be Faster to Start

TCP requires connection establishment.

Conceptually:

```text

connection setup

```

UDP:

```text
UDP:

```

Therefore UDP avoids the TCP connection-establishment delay.

This does **not** mean UDP is always faster in every application. It means it avoids that particular connection-setup mechanism.

# 25. UDP Checksum

The slide on **page 13** introduces the purpose:

> Goal: detect “errors” (e.g., flipped bits) in the transmitted segment.

The checksum is an **error-detection mechanism**.

It is not a complete reliability mechanism.

---

# 26. What Does “Flipped Bit” Mean?

A bit flip means:

```text
0 → 1
```

or:

```text
1 → 0
```

Example:

```text
Original:
10110100

Corrupted:
10100100
```

One bit has changed.

The checksum attempts to detect such corruption.

---

# 27. Why Does UDP Need a Checksum?

The study notes provide an important explanation.

One might ask:

> If link-layer protocols can also perform error checking, why does UDP need a checksum?

Because:

1. Not every link-layer protocol necessarily provides the same error checking.
2. A segment can potentially be corrupted while stored in a router's memory.
3. UDP should provide end-to-end error detection rather than relying completely on every underlying link.

Therefore:

```text
Link-level error detection
        +
UDP end-to-end checksum
```

provides an additional layer of protection.

---

# 28. Important Limitation of the Checksum

UDP checksum provides:

```text
Error detection
```

It does NOT automatically provide:

```text
Error correction
Retransmission
Reliable delivery
Ordering
```

Therefore:

> **Checksum ≠ reliability.**

# 29. UDP Checksum Algorithm

The sender:

1. treats the relevant data as a sequence of 16-bit words
2. adds the words using one's-complement addition
3. wraps any carry-out around to the least significant end
4. takes the one's complement of the final sum
5. places that result into the checksum field

In shorthand:

```text
16-bit words
     ↓
one's-complement addition
     ↓
end-around carry
     ↓
one's complement
     ↓
CHECKSUM
```

---

# 30. What Is One's-Complement Addition?

Normal binary addition can produce:

```text
carry out
```

from the most significant bit.

In one's-complement addition, that carry is **wrapped around** and added back into the least significant bit.

Example:

```text
  1111111111111111
+ 0000000000000001
------------------
1 0000000000000000
```

Wrap the carry:

```text
0000000000000000
+
0000000000000001
----------------
0000000000000001
```

The final result is the one's-complement sum.

---

# 31. End-Around Carry

This is one of the most important checksum rules.

If addition produces:

```text
1 XXXXXXXX XXXXXXXX
^
carry
```

do:

```text
XXXXXXXX XXXXXXXX
+
00000000 00000001
```

The carry is added back to the low-order end.

### Memory

```text
Carry out
   ↓
wrap around
   ↓
add to LSB
```

---

# 32. One's Complement

After obtaining the final one's-complement sum:

```text
0 → 1
1 → 0
```

Example:

```text
Sum:
10110010

One's complement:
01001101
```

That complemented value becomes the checksum.

---

# 33. Receiver Checksum Procedure

The receiver does not simply calculate a fresh checksum and compare strings.

Instead, it:

1. takes the received UDP segment
2. includes the received checksum
3. adds all relevant 16-bit words using one's-complement addition
4. checks the final result

If there is no detected error:

```text
1111111111111111
```

is obtained before the final complement check.

Equivalently:

```text
complement = 0000000000000000
```

If the expected result is not obtained:

```text
possible error
```

---

# 37. Page 15 — Five Steps of Computing UDP Checksum

The slide gives a five-step procedure.

## Step 1 — Split into 16-bit words

Treat the header fields and data as a sequence of 16-bit words.

---

## Step 2 — Add the words together

Use ordinary binary addition as the basis of each addition.

---

## Step 3 — Handle wraparound carry

If there is a carry out of the most significant bit:

```text
carry → add it back
```

Do not discard it.

---

## Step 4 — The result is the SUM

Continue adding all words, performing end-around carry whenever required.

---

## Step 5 — Flip every bit

Take the one's complement.

That final value is:

```text
CHECKSUM
```

# 42. Why Can the Checksum Miss an Error?

The checksum is based on arithmetic aggregation.

If errors occur in patterns that compensate for one another, the final checksum may remain unchanged.

Example concept:

```text
Word 1:
...10

Word 2:
...01
```

Change to:

```text
Word 1:
...01

Word 2:
...10
```

The total contribution can remain the same.

Therefore:

```text
data changed
+
checksum unchanged
=
error may escape detection
```

---

# 43. “Weak Protection” Does NOT Mean Useless

The checksum is useful for detecting many accidental transmission errors.

But it is not mathematically guaranteed to detect every possible corruption pattern.

Thus:

```text
Checksum = error detection
not
Checksum = perfect error detection
```

---

# 44. Types of Errors That Can Be Missed

The slide on **page 18** summarizes patterns that can escape the checksum.

### 1. A single bit flip

A single bit error generally changes the sum and is therefore detected.

---

### 2. Some two-bit patterns

Errors in opposite directions can cancel.

Example:

```text
one 0 → 1
one 1 → 0
```

can potentially produce no change in the total.

---

### 3. Certain multi-bit errors

Some multi-word or structured error patterns can produce the same checksum.

---

### 4. All-zero/all-one patterns

The slide highlights special cases involving patterns of zeros/ones.

The key principle remains:

> If the arithmetic effect of the corruption leaves the checksum unchanged, the error can pass undetected.

---

# 45. Strong vs Weak Error Detection

The checksum is described as **weak protection** because collisions are possible.

A checksum is not cryptographic integrity protection.

For exam purposes:

```text
Checksum:
detects many accidental errors
but can miss some error patterns
```

# 59. UDP Checksum — Complete Algorithm

## Sender

```text
1. Take UDP segment/checksum input.
2. Divide into 16-bit words.
3. Add all words.
4. If carry occurs, wrap it around.
5. Continue until all words are added.
6. Take one's complement.
7. Put result in checksum field.
```

## Receiver

```text
1. Receive segment.
2. Take all relevant 16-bit words including checksum.
3. Add using one's-complement arithmetic.
4. Perform end-around carry.
5. Check whether result is all 1s.
6. If valid → accept/no error detected.
7. Otherwise → error detected.
```

# 60. Checksum vs Error Correction

The checksum does not tell the receiver:

```text
"Here is the original correct bit."
```

It only provides evidence that:

```text
the received data is probably unchanged
```

Therefore:

```text
Detection ≠ correction
```

If an application requires recovery from corruption/loss, it needs additional mechanisms.

---

# 61. UDP Reliability Is Different from UDP Checksum

This distinction is critical.

### Checksum

```text
Detects possible corruption.
```

### Reliability

Requires mechanisms such as:

```text
ACKs
Sequence numbers
Retransmissions
Timers
Ordering
```

UDP's checksum alone does not supply those mechanisms.

# 62. UDP Does Not Use TCP-Style Congestion Control

The study notes explain that TCP has congestion-control mechanisms that can throttle a sender during congestion.

UDP does not provide equivalent built-in TCP congestion control.

Therefore:

```text
UDP sender
→ application largely controls sending rate
```

This is one reason UDP can be useful for applications with their own rate-control requirements.

From the study notes:


This is relatively small compared with TCP.

Therefore, if an application does not need TCP's connection establishment and reliability machinery, UDP can reduce transport-layer overhead.

# 68. Why Checksum Is End-to-End

The study notes connect UDP checksum to the **end-to-end principle**.

A packet can encounter many links:

```text
Host A
 ↓

 ↓
Router
 ↓
Link 2
 ↓
Router
 ↓
Link 3
 ↓
```

Not every link necessarily provides the same error checking.

Therefore the endpoints can perform their own integrity check.

# 69. UDP Best-Effort Service

“Best effort” means:

```text
UDP sends the datagram
and does not promise successful delivery.
```

There is no built-in guarantee that:

- destination receives it
- destination receives it once
- destination receives it in order
- destination receives it without corruption

The checksum can detect many corruption cases, but UDP does not automatically repair them.

This means UDP does not maintain a TCP-like connection state for a stream of segments.

```text
Segment 2 → independent
Segment 3 → independent
```

This contributes to UDP's simplicity.

A sender can transmit a datagram without first establishing a transport connection.

# 74. Checksum Numerical Problems — Exact Method

When you see:

> Find checksum for 3/4 binary words.

Do this:

### Step 1

Write every word as exactly 16 bits.

```text
xxxxxxxxxxxxxxxx
xxxxxxxxxxxxxxxx
xxxxxxxxxxxxxxxx
```

### Step 2

Add first two.

### Step 3

If there is a 17th bit:

```text
carry = 1
```

wrap it around.

### Step 4

Add the next word.

### Step 5

Again wrap any carry.

### Step 6

After the final sum:

```text
flip every bit
```

### Step 7

That is the checksum.

# 75. Numerical Example Template

Suppose:

```text
W1 = 1010101010101010
W2 = 0101010101010101
```

Do:

```text
  1010101010101010
+ 0101010101010101
------------------
  1111111111111111
```

No carry.

Complement:

```text
0000000000000000
```

Therefore checksum:

```text
0000000000000000
```

The exact numerical result depends on the supplied words.

# 76. Receiver Verification Template

Given:

```text
W1
W2
W3
CHECKSUM
```

calculate:

```text
W1 + W2 + W3 + CHECKSUM
```

using one's-complement addition.

If:

```text
1111111111111111
```

then:

```text
No error detected.
```

If not:

```text
Error detected.
```

# 77. Why End-Around Carry Matters

Suppose:

```text
  1111111111111110
+ 0000000000000010
------------------
1 0000000000000000
```

Do NOT simply take:

```text
0000000000000000
```

Instead wrap:

```text
0000000000000000
+
0000000000000001
----------------
0000000000000001
```

This is the essential difference between ordinary addition and one's-complement addition.

# 78. Error Pattern Example

Suppose two bits are changed in opposite directions.

Original:

```text
...10
...01
```

Changed:

```text
...01
...10
```

The numerical total can remain unchanged.

Therefore:

```text
checksum before
=
checksum after
```

even though:

```text
data before
≠
data after
```

This is the exact conceptual point of the **“Weak protection!”** slide.

# 79. Why the Checksum Is Still Useful

Even though it can miss certain patterns, it detects many common accidental bit errors.

Therefore it provides a lightweight integrity check without requiring a large amount of processing or header overhead.

The correct statement is:

> UDP checksum provides error detection with limited protection, not guaranteed error detection and not error correction.

# 81. High-Yield Definitions

### UDP

A connectionless, best-effort transport protocol with low overhead that does not provide TCP-style reliable ordered delivery.

### Connectionless

No transport-layer handshake/connection establishment occurs before sending UDP data.

### Checksum

A value calculated from the segment's contents and used for error detection.

### One's-complement addition

Binary addition in which any carry out of the most significant bit is wrapped around and added to the least significant bit.

### End-around carry

The carry from the most significant bit is added back to the least significant end.

### One's complement

Every bit is inverted:

```text
0 → 1
1 → 0
```

### Demultiplexing

Delivering an incoming transport segment to the correct application socket.
