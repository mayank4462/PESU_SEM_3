# 1. Transport Layer — Big Picture

The transport layer extends **host-to-host delivery** into **process-to-process delivery**.

### Network layer

```text
Host A  ───────────────→  Host B
```

The network layer gets packets from one host to another.

### Transport layer

```text
Process P1 ───────────→ Process P4
```

The transport layer gets application data to the correct process/socket on the destination host.

### Core distinction

> **Network layer = host-to-host**
>
> **Transport layer = process-to-process**

This is the central idea behind multiplexing and demultiplexing.

---

# 2. Why Do We Need Multiplexing/Demultiplexing?

A single host can run many network applications simultaneously.

Example:

```text
Laptop
 ├── Browser
 ├── WhatsApp
 ├── SSH
 ├── Video call
 └── DNS client
```

All of these applications may use the same network connection and the same IP address.

The transport layer must determine:

> **Which incoming data belongs to which application process?**

This is accomplished using **port numbers** and sockets.

---

# 3. Application-Layer Message → Transport Segment

At the sender:

```text
Application process
       ↓
Application message
       ↓
Transport layer
       ↓
Transport segment
       ↓
Network layer
```

The transport layer takes the application message and adds a transport header.

The result is a **transport-layer segment**.

For UDP, it is commonly called a **UDP datagram**.

For TCP, it is a **TCP segment**.

---

# 4. Socket — The Interface

A **socket** is the interface between an application process and the transport layer.

```text
Application Process
        ↕
      Socket
        ↕
Transport Layer
```

Think of the socket as a **door** through which application data enters or leaves the transport layer.

### Important

The application does not directly construct IP packets and send them through the physical network.

It communicates through its socket.

---

# 5. IP Address vs Port Number

These two are extremely important.

## IP address

Identifies the **host**.

Example:

```text
192.168.1.10
```

## Port number

Identifies the **application endpoint/socket** on that host.

Example:

```text
192.168.1.10 : 80
```

means:

```text
Host = 192.168.1.10
Port = 80
```

### Memory trick

> **IP → Which machine?**
>
> **Port → Which application/socket?**

---

# 6. Port Numbers

Port numbers are **16-bit numbers**.

Range:

```text
0 to 65535
```

The slides specifically note:

- ports 0–1023 are well-known/restricted/reserved
- higher ports are available for other applications

Examples from the slide deck's quick-reference table:

| Service | Transport | Port |
|---|---|---:|
| FTP data/control | TCP | 20 / 21 |
| SSH | TCP | 22 |
| Telnet | TCP | 23 |
| SMTP | TCP | 25 |
| DNS | TCP/UDP | 53 |
| DHCP | UDP | 67 / 68 |
| HTTP | TCP | 80 |
| HTTPS | TCP | 443 |

### Exam trap

A port number does **not** identify the host.

The IP address identifies the host.

# 7. Multiplexing at the Sender

The slide on **page 9** explicitly shows the sender performing multiplexing.

Multiple application sockets/processes produce data:

```text
P3 ──┐
     │
P1 ──┼──→ Transport layer → network
     │
P2 ──┘
```

The transport layer:

1. handles data from multiple sockets
2. adds a transport header
3. creates transport segments
4. passes them to the network layer

### Definition

> **Multiplexing at the sender = collecting data from multiple sockets, adding transport-layer header information, and passing the resulting segments to the network layer.**

---

# 8. Demultiplexing at the Receiver

At the receiver, the reverse process occurs.

The transport layer receives segments from the network layer and determines which socket should receive each segment.

```text
Incoming segments
       ↓
Transport layer
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
P1    P2    P4
```

The slide on **page 9** describes this as:

> using header information to deliver received segments to the correct socket.

### Definition

> **Demultiplexing = delivering each received transport segment to the appropriate receiving socket.**

---

# 9. Multiplexing vs Demultiplexing

| Multiplexing | Demultiplexing |
|---|---|
| Sender side | Receiver side |
| Multiple sockets → transport | Transport → correct socket |
| Adds transport header | Uses transport header |
| Combines data from application processes | Delivers data to correct application process |

### One-line memory

```text
MULTIPLEX = many → one
DEMULTIPLEX = one incoming flow → correct many
```

# 10. Every Layer Performs a Similar Job

The slide on **page 19** gives a useful analogy across layers.

| Layer | What sorts/identifies traffic | Analogy |
|---|---|---|
| Transport | Port numbers | Mailbox numbers |
| Network | Protocol field in IP header | Sorting street/address information |
| Link | EtherType field | Building/door routing |

The important concept is that each layer uses its own header information to determine where the data belongs next.

# 11. UDP Multiplexing/Demultiplexing

UDP is **connectionless**.

Therefore, UDP does not maintain a connection state for each communication pair.

UDP uses port information to direct datagrams to sockets.

The UDP header includes:

```text
Source port
Destination port
Other UDP header fields
Application data
```

The slide on **page 10** shows the UDP datagram format with:

```text
source port #
dest port #
other header fields
application data
```

---

# 12. UDP Datagram Structure

Simplified:

```text
+-------------------+-------------------+
| Source Port       | Destination Port  |
+-------------------+-------------------+
| Other UDP Header Fields               |
+---------------------------------------+
| Application Data / Payload            |
+---------------------------------------+
```

The source and destination ports are each **16 bits**.

Therefore:

```text
UDP port number = 16 bits
```

---

# 13. UDP Demultiplexing

When a host receives a UDP segment:

1. it receives the datagram from IP
2. examines the destination port number
3. identifies the UDP socket associated with that destination port
4. delivers the datagram to that socket

### Core rule

> **UDP demultiplexing uses the destination port number.**

---

# 14. UDP Destination Port Example

Suppose:

```text
Destination port = 9157
```

The receiving host checks which UDP socket is bound to port 9157.

If:

```text
Datagram destination port = 9157
```

then:

```text
UDP → socket bound to 9157
```

The application attached to that socket receives the data.

---

# 15. UDP Source Port

The source port identifies the sending application's socket.

It is useful for identifying where a response should be sent.

Example:

```text
Client:
IP = A
Source port = 9157

Server:
IP = B
Destination port = 6428
```

The server can use the source address/port information when sending a response back.

---

# 16. UDP: Same Destination Port

The slide on **page 11** contains an important case.

Suppose a host receives UDP datagrams with:

```text
same destination port #
```

but different source IP addresses and/or source ports.

For example:

```text
Datagram 1:
source IP = A
source port = 9157
destination port = 6428

Datagram 2:
source IP = B
source port = 9157
destination port = 6428
```

Both can be directed to the same UDP socket because their destination port is the same.

### Important

For ordinary UDP demultiplexing in this model:

> **Datagrams with the same destination port can be delivered to the same socket even if their source IP addresses or source ports differ.**

---

# 17. UDP Socket Creation Example

A UDP socket can be created using:

```python
clientSocket = socket(AF_INET, SOCK_DGRAM)
```

Where:

```text
AF_INET
→ IPv4

SOCK_DGRAM
→ UDP datagram socket
```

A socket can be bound to a local port:

```python
clientSocket.bind(('', 19157))
```

This means the socket is associated with local port `19157`.

# 18. UDP Send/Receive Logic

A UDP sender specifies:

```text
Destination IP address
Destination port
```

The receiver uses:

```text
Destination port
```

to locate the appropriate UDP socket.

Conceptually:

```text
Application
    ↓
UDP socket
    ↓
UDP datagram
    ↓
IP
    ↓
Network
    ↓
IP
    ↓
UDP
    ↓
Destination UDP socket
    ↓
Application
```

# 19. UDP Is Connectionless

The slide summary on **page 15** emphasizes an important difference:

> UDP has no notion of an ongoing connection.

Each UDP datagram is handled independently.

There is no TCP-style connection state that identifies the datagram as belonging to a particular ongoing connection.

### Therefore

UDP demultiplexing can use the destination port without needing the full TCP-style connection identification.

---

# 20. TCP Multiplexing/Demultiplexing

TCP is different.

A TCP connection is identified using a **4-tuple**:

```text
(source IP address,
 source port number,
 destination IP address,
 destination port number)
```

This is explicitly shown on **page 13** of the slide deck.

### Memorize

> **TCP connection = 4-tuple**

---

# 21. TCP 4-Tuple Example

Suppose:

```text
Client:
IP = A
Source port = 49157

Server:
IP = B
Destination port = 80
```

The connection is:

```text
(A, 49157, B, 80)
```

A TCP segment belonging to that connection is delivered according to this connection identity.

---

# 22. Why TCP Needs the Full 4-Tuple

A server may have many simultaneous TCP connections.

Example:

```text
Server
  |
  ├── Client 1
  ├── Client 2
  ├── Client 3
  └── Client 4
```

All clients may connect to:

```text
Server IP = B
Server port = 80
```

Yet the server must distinguish the connections.

The source IP and source port make this possible.

---

# 23. TCP Example from the Slide — Multiple Clients

The slide on **page 14** shows:

```text
Host A
  P1

Host B
  P4, P5, P6

Host C
  P2, P3
```

Multiple clients connect to the same web server.

All segments are destined for:

```text
Server port = 80
```

but they belong to different TCP connections because their full 4-tuples differ.

# 24. Same Server, Same Destination Port, Different Clients

Suppose:

```text
Client A:
source IP = A
source port = 49157
destination IP = B
destination port = 80

Client C:
source IP = C
source port = 775
destination IP = B
destination port = 80
```

Both have:

```text
destination IP = B
destination port = 80
```

But they are different TCP connections because:

```text
source IP
and/or
source port
```

are different.

### Critical MCQ point

> **A TCP server can have many simultaneous connections using the same destination/server port.**

---

# 25. Why One Server Can Handle Many TCP Connections

A web server might listen on:

```text
port 80
```

Many clients connect to port 80.

The server does not need a different server port for every client.

Instead, each TCP connection is identified by its unique 4-tuple.

Thus:

```text
Same server port
+
Different client endpoints
=
Different TCP connections
```

---

# 26. Listening Socket vs Connection Socket

For a TCP server, there is a distinction between:

### Welcoming/listening socket

Used to accept incoming connection requests.

### Connection socket

Created/used for communication with a particular client.

Conceptually:

```text
                 Server
                   |
          Listening socket
                   |
        ┌──────────┼──────────┐
        ↓          ↓          ↓
    Client 1    Client 2    Client 3
   connection  connection  connection
     socket      socket      socket
```

This is why a server can support many TCP connections simultaneously.

# 27. TCP Socket Identification

The slide states that a TCP socket is identified by four values:

```text
source IP address
source port number
destination IP address
destination port number
```

This is the **4-tuple**.

### Do not confuse

UDP demultiplexing:

```text
destination port
```

TCP connection-oriented demultiplexing:

```text
4-tuple
```

This distinction is highly testable.

# 28. UDP vs TCP Demultiplexing

| Feature | UDP | TCP |
|---|---|---|
| Connection state | No ongoing connection | Connection state maintained |
| Main identification | Destination port | Full 4-tuple |
| Can same destination port serve many sources? | Yes | Yes |
| Connection-specific state | No | Yes |
| Connection identity | Not based on full 4-tuple | 4-tuple |

### Memory

```text
UDP → destination port
TCP → 4-tuple
```

# 29. Why Does UDP Need Only the Destination Port?

UDP does not maintain a separate connection state for every sender.

A UDP socket can receive datagrams from different sources.

If they have the same destination port, they can be delivered to the same socket.

Example:

```text
A:9157 → B:6428
C:9157 → B:6428
D:3000 → B:6428
```

All can reach the UDP socket associated with:

```text
B:6428
```

---

# 30. Why Does TCP Need the Full 4-Tuple?

TCP maintains state for each individual connection.

Therefore, the transport layer must know:

```text
Which source?
Which source port?
Which destination?
Which destination port?
```

That combination uniquely identifies the TCP connection in the normal model.

# 31. HTTP Example

Suppose a web server is:

```text
Server IP = B
Server port = 80
```

Three clients connect:

```text
Client A → B:80
Client C → B:80
Client D → B:80
```

All three use destination port 80.

But each connection has a different 4-tuple.

Therefore the server can direct each incoming segment to the correct connection socket.

# 36. Study-Notes Addition — Transport-Layer Services

The Highlight Study Notes place multiplexing/demultiplexing within the broader transport-layer role.

Transport-layer responsibilities include:

### Process-to-process delivery

Data is delivered to the correct application process.

### Reliable data transfer — TCP

TCP uses mechanisms such as:

- acknowledgments
- retransmissions
- sequence numbers
- timers

### UDP

UDP provides:

- connectionless transport
- checksum/error detection
- low overhead

but does not guarantee:

- delivery
- ordering
- retransmission
- flow control
- congestion control

---

# 37. Study-Notes Addition — Reliable Data Transfer Connection

Multiplexing tells us:

> **Which application gets the data?**

Reliable data transfer tells us:

> **How TCP makes sure the data arrives correctly and in order.**

TCP uses:

```text
Sequence numbers
      +
ACKs
      +
Timers
      +
Retransmission
```

These mechanisms are separate from the basic demultiplexing function but operate in the same transport layer.

---

# 38. Study-Notes Addition — Flow Control

TCP also provides **flow control**.

Problem:

```text
Sender →→→→→ Receiver
```

If the sender is faster than the receiver, the receiving buffer can overflow.

TCP uses the receiver window:

```text
rwnd
```

to limit how much unacknowledged data can be in flight.

### Important distinction

```text
Flow control
→ protects receiver
```

while:

```text
Congestion control
→ protects network
```

---

# 39. Study-Notes Addition — TCP Sequence Numbers

TCP sequence numbers identify **bytes**, not simply packets.

If a segment starts at byte 1000 and contains 500 bytes:

```text
First byte = 1000
Next expected byte = 1500
```

This sequence-number mechanism supports reliable ordered delivery.

---

# 40. Study-Notes Addition — TCP ACKs

TCP acknowledgments are generally cumulative.

If the receiver sends:

```text
ACK = 1500
```

it indicates that the receiver is expecting byte 1500 next, meaning preceding bytes have been received in order.

This helps TCP determine which data has successfully arrived.

---

# 41. Study-Notes Addition — TCP Three-Way Handshake

Before normal TCP data transfer:

```text
Client                     Server

SYN  -------------------->

     <-------------------- SYNACK

ACK  -------------------->
```

Purpose:

- establish connection state
- exchange initial sequence numbers
- confirm both directions

### Memory

```text
SYN → SYNACK → ACK
```

---

# 42. Study-Notes Addition — RTT and Timeout

TCP uses timers to detect possible loss.

If the expected ACK does not arrive before timeout:

```text
Timeout
   ↓
Possible loss
   ↓
Retransmission
```

TCP estimates RTT so that the timeout is not:

- too short → unnecessary retransmissions
- too long → slow recovery

# 43. Connectionless vs Connection-Oriented

## UDP — connectionless

```text
Datagram 1 → independently handled
Datagram 2 → independently handled
Datagram 3 → independently handled
```

No ongoing connection state is required.

## TCP — connection-oriented

```text
Connection
    ↓
State maintained
    ↓
Segments associated with that connection
```

This is why TCP uses the 4-tuple to identify each connection.

# 45. Exam Questions from the Slides — Explained

## Q1. Why does TCP need a connection "setup" step before any data flows, while UDP does not?

### Answer

TCP is connection-oriented.

It establishes shared connection state between sender and receiver, including sequence-number information and other state required for reliable communication, flow control and congestion control.

UDP is connectionless and can send individual datagrams without establishing an ongoing connection.

---

## Q2. Name two things neither TCP nor UDP guarantees.

Possible answers:

- delay guarantees
- bandwidth guarantees

Neither standard TCP nor UDP guarantees a specific end-to-end delay or bandwidth.

---

## Q3. A segment header's first 32 bits hold two fields. What are they?

```text
Source port #
Destination port #
```

Each is:

```text
16 bits
```

Therefore:

```text
16 + 16 = 32 bits
```

---

## Q4. If two applications on one laptop both try to bind to port 5775 at the same time, what happens?

Normally, the second application cannot bind to the same local port/socket combination while it is already in use, unless special socket options or a different address/binding arrangement allow it.

### Exam-level answer

> Two independent applications cannot normally bind the same local port at the same time.

---

## Q5. Why is DNS often sent over UDP rather than TCP?

The slide's conceptual point is:

- DNS queries are typically small
- a DNS request/response can often be handled without TCP connection setup
- UDP has lower overhead

Therefore UDP can provide faster/simple request-response behavior.

DNS can also use TCP when required.

---

# 46. More Exam Questions — TCP 4-Tuple

## Q6. What would break if TCP demultiplexing used only the destination port?

Suppose many clients connect to:

```text
Server B:80
```

If only destination port were considered, all clients would appear identical.

The server would not know which connection a segment belongs to.

Therefore TCP uses the full 4-tuple.

---

## Q7. Two TCP segments have the same destination IP and destination port but different source ports. Same connection?

### Answer

No.

Different source ports generally indicate different TCP connections.

---

## Q8. Two TCP connections can use the same destination port. True or false?

### Answer

**True.**

Example:

```text
Client A:49157 → Server B:80
Client C:775   → Server B:80
```

Destination port is the same, but the 4-tuples differ.

---

## Q9. Can two UDP datagrams with different source IPs be delivered to the same socket?

### Answer

**Yes**, if their destination port identifies the same UDP socket under the slide's UDP demultiplexing model.

---

## Q10. Which uses the full 4-tuple for demultiplexing?

### Answer

**TCP connection-oriented demultiplexing.**

# 47. High-Yield MCQ Traps

### Trap 1

> IP address identifies the application.

❌ False.

IP identifies the host.

Port identifies the application endpoint.

---

### Trap 2

> Multiplexing happens at the receiver.

❌ False.

Multiplexing → sender.

Demultiplexing → receiver.

---

### Trap 3

> UDP uses the complete 4-tuple to identify the receiving socket.

❌ In the slide's model.

UDP uses the destination port for demultiplexing.

---

### Trap 4

> TCP uses only destination port to identify a connection.

❌ False.

TCP uses:

```text
source IP
source port
destination IP
destination port
```

---

### Trap 5

> Two TCP connections cannot have the same destination port.

❌ False.

Many clients can connect to the same server port.

---

### Trap 6

> UDP has connection state like TCP.

❌ False.

UDP is connectionless.

---

### Trap 7

> A port number is 32 bits.

❌ False.

Port number = **16 bits**.

---

### Trap 8

> Source and destination port together occupy 32 bits.

✅ True.

```text
16 + 16 = 32
```

---

### Trap 9

> TCP is only used for one client at a time.

❌ False.

A server can maintain many simultaneous TCP connections.

---

### Trap 10

> UDP checksum provides reliable delivery.

❌ False.

Checksum detects errors; it does not provide retransmission or guaranteed delivery.

               ┌────────┴────────┐
               |                 |
              UDP               TCP
               |                 |
        Connectionless    Connection-oriented
               |                 |
        Destination port       4-tuple

        ↓

```

   ↓
Transport segments
   ↓
Demultiplexing
   ↓
Correct socket
   ↓

```

# 51. One-Minute Revision

> **Transport layer = process-to-process delivery.**
>
> **Socket = interface between application and transport layer.**
>
> **IP address = host.**
>
> **Port number = application endpoint.**
>
> **Multiplexing = sender collects data from multiple sockets and adds transport headers.**
>
> **Demultiplexing = receiver uses transport-header information to deliver segments to the correct socket.**
>
> **UDP demultiplexing = destination port.**
>
> **TCP connection identification = 4-tuple: source IP, source port, destination IP, destination port.**
>
> **UDP = connectionless.**
>
> **TCP = connection-oriented.**
>
> **Port numbers = 16 bits, 0–65535.**
>
> **TCP can have many simultaneous connections to the same server port.**
>
> **Flow control protects receiver; congestion control protects network.**
>
> **TCP reliability = sequence numbers + ACKs + timers + retransmission.**
